A callback URL is the web address the login service sends the user's browser back to once login is finished. Something must be running at that address to receive the result; during testing, that "something" is a small temporary web server on your own computer, called a callback server.

Why login results arrive this way

You might expect your code to call Cognito and simply get tokens back. For logins involving a user, it does not work like that, because the user must type their password on Cognito's (or Google's) own page, not in your app. So the flow is:

  1. Your app sends the user's browser to the login page.
  2. The user logs in there.
  3. The login service sends the browser back to the callback URL, attaching a short-lived authorization code, for example: https://app.example.com/callback?code=abc123&state=xyz.
  4. Whatever is listening at that URL picks up the code and swaps it with Cognito for real tokens.

The code is a claim ticket, not the prize: it is worthless without the app's client secret or PKCE proof, and it expires within minutes.

Why an authorization code? Why not send the tokens directly?

Because the redirect back to your app travels through the browser, where it is easy to see and steal, while the code-for-tokens swap travels directly between your app and Cognito, where nobody else can see it. The code is a harmless claim ticket; the tokens are the valuables, so they never ride through the browser.

Two kinds of channel

  • The front channel is anything passed through the user's browser: redirects and the addresses they carry. It is the only way to bring the user back to your app, but it is leaky. Addresses end up in browser history, server logs and proxy logs, can be read by browser extensions, and on phones can be grabbed by a malicious app that registers the same callback address.
  • The back channel is a direct HTTPS request from your app (or its server) to Cognito's /oauth2/token address. Nothing passes through the browser, and the app chose whom it is talking to.

The authorization code flow puts only the code on the front channel and the tokens on the back channel.

Why that split matters

  1. A stolen code is useless on its own. To swap it, the thief would also need the client secret or the PKCE code verifier, which never appeared in the browser. A stolen token would work immediately.
  2. The code is short-lived and single-use. It expires within minutes and Cognito accepts it only once, so even a leaked code has a tiny window.
  3. The app proves who it is at the swap. The redirect cannot prove which app receives it, but the token request can, with the client secret or PKCE. Tokens are only ever handed to the genuine app.
  4. Refresh tokens become possible. Long-lived refresh tokens are too dangerous to put in a browser address, so a token-in-the-redirect design gives none, and users must log in again every hour. The back channel can safely deliver one.
  5. The app knows the tokens are genuine and meant for it. Tokens arrive as the answer to a request the app itself made, so an attacker cannot slip in a stolen token by crafting a fake redirect (a token injection attack).

The old way: the implicit flow

OAuth used to offer exactly what you are asking about. In the implicit flow (response_type=token), the tokens came back in the redirect itself, after a # in the address. It was designed in the days before browsers could make cross-site requests, when single-page apps had no other option.

Implicit flow (tokens in the redirect) Authorization code flow (+ PKCE)
What travels through the browser The tokens themselves Only a short-lived, single-use code
If the redirect is intercepted The attacker can use the tokens right away The attacker cannot swap the code without the secret or verifier
Proves which app receives the tokens No Yes, with the client secret or PKCE
Refresh token Not issued Issued
Exposure in history, logs, extensions High Only the harmless code
Status today Discouraged by current OAuth security guidance and dropped from OAuth 2.1 The recommended flow for every kind of app

Cognito still lets an app client enable the implicit grant for older apps. Leave it switched off, and use the authorization code flow with PKCE instead.

An analogy

A courier with a valuable parcel doesn't leave it on your doorstep, where anyone walking by could take it. They leave a collection slip (the code) in your letterbox. You then go to the depot counter (the back channel) and show the slip and your ID (the client secret or PKCE verifier) to collect the parcel (the tokens). Someone who steals the slip from your letterbox still can't collect your parcel.

Two safety features:

  • Exact registration. Cognito only sends users back to callback URLs you registered on the app client. This stops an attacker tricking Cognito into delivering codes to their own website.
  • The state value. The app sends a random value at the start and checks it comes back unchanged. This blocks a forged login response.

Callback URLs at each link of the chain

Relationship Where it is registered Address
Cognito sends the user back to your app Your app client in the User Pool https://app.example.com/callback
Google sends the user back to Cognito Google Cloud Console https://<your-domain>.auth.<region>.amazoncognito.com/oauth2/idpresponse

Testing vs production

Testing (a notebook, script or command-line tool) Production
What is listening A temporary mini web server on your own computer, at http://localhost:<port>/callback A /callback page on your real website or backend server
Registered address e.g. http://localhost:8080/callback. Cognito allows plain http only for localhost An https:// address on your domain
How long it runs Only for the few seconds of the login, then it shuts down All the time
Who swaps the code for tokens Your script, usually with PKCE Your server using the client secret, or the browser app using PKCE
Mobile apps Not applicable A special app link such as myapp://callback that opens your app

Why testing needs a callback server

A Jupyter notebook or a Python script has no website, so when the browser is sent back after login, there is nowhere for it to go. Starting a tiny server on localhost gives the browser somewhere to land, and lets the script catch the code. Familiar tools do the same: gcloud auth login and gh auth login briefly start a local server for exactly this reason. It is the recommended pattern for desktop and command-line apps.

What a callback server actually does: its methods

A callback server is small. For an ordinary Cognito login it answers one main route, GET /callback, plus an optional health check; everything else is helper code around it. Agent platforms add one more route of their own.

The routes it answers

Route HTTP method Called by What it does
/callback GET The user's browser, redirected by Cognito after login Reads code and state (or error), checks state, swaps the code for tokens, shows a "you can close this tab" page
/ping or /health (optional) GET Your own script or a load balancer Confirms the server is running before the login starts
Agent callback, e.g. /oauth2/callback?session_id=... (agent platforms only) GET The browser, redirected by AgentCore Identity after the user approves an outside service Checks the logged-in user, then calls CompleteResourceTokenAuth (see below)

The main route is a GET because the browser arrives by following a redirect, and redirects are always followed with GET; the code travels in the address's query string. Some identity providers can post the result to the callback instead (response_mode=form_post, a POST), but Cognito's standard flow uses GET.

What happens inside the /callback handler, step by step

  1. Read the query string. On success it holds code and state. If the user cancelled or something failed, it holds error (for example access_denied) and error_description instead; show that to the user and stop.
  2. Check state. It must equal the random value the app created just before sending the user to log in. A mismatch means the response may be forged, so reject it.
  3. Swap the code for tokens. Send a POST to Cognito's token address, https://<your-domain>.auth.<region>.amazoncognito.com/oauth2/token, with a form body containing grant_type=authorization_code, the code, the same redirect_uri used at the start (it must match exactly), the client_id, and either the PKCE code_verifier or the client secret (sent in an Authorization: Basic header).
  4. Receive the tokens. Cognito replies with JSON containing id_token, access_token, refresh_token, expires_in and token_type.
  5. Check the ID token before trusting it: signature, issuer, audience (your client ID) and expiry.
  6. Hand the tokens over. In testing, pass them to the waiting script in memory. In production, store them on the server and give the browser a session cookie.
  7. Answer the browser. In testing, a plain "Login complete, you can close this tab" page. In production, a redirect to the app's home page.
  8. Shut down (testing only). The temporary server stops once it has the tokens, or after a timeout such as two minutes.

Helper functions around it

  • Start the login: pick a port, create state and the PKCE verifier and challenge, build the /oauth2/authorize address, and open the browser.
  • Wait: block until the callback has delivered tokens or an error, with a timeout.
  • Refresh (production): later, POST to /oauth2/token with grant_type=refresh_token to get new tokens without a new login.

A minimal local callback server in Python (standard library only)

import base64, hashlib, http.server, json, secrets, threading, urllib.parse, urllib.request, webbrowser

DOMAIN = "https://my-app.auth.us-east-1.amazoncognito.com"
CLIENT_ID = "4abcexampleclientid"
REDIRECT_URI = "http://localhost:8080/callback"   # registered on the app client

state = secrets.token_urlsafe(16)                   # CSRF protection
verifier = secrets.token_urlsafe(64)                # PKCE secret, never leaves this script
challenge = base64.urlsafe_b64encode(hashlib.sha256(verifier.encode()).digest()).rstrip(b"=").decode()
result, done = {}, threading.Event()

class CallbackHandler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):                               # the browser returns here with GET
        url = urllib.parse.urlparse(self.path)
        if url.path == "/ping":                     # optional health check
            return self.reply(200, "ok")
        if url.path != "/callback":
            return self.reply(404, "Not found")
        q = urllib.parse.parse_qs(url.query)
        if "error" in q:                            # user cancelled or login failed
            result["error"] = q["error"][0]
        elif q.get("state", [""])[0] != state:      # forged or stale response
            result["error"] = "state mismatch"
        else:
            result["tokens"] = exchange_code(q["code"][0])
        self.reply(200, "Login complete. You can close this tab.")
        done.set()

    def reply(self, status, text):
        self.send_response(status)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.end_headers()
        self.wfile.write(text.encode())

def exchange_code(code):                            # POST the code to Cognito's token address
    body = urllib.parse.urlencode({
        "grant_type": "authorization_code", "code": code,
        "redirect_uri": REDIRECT_URI, "client_id": CLIENT_ID,
        "code_verifier": verifier,                  # PKCE proof instead of a client secret
    }).encode()
    req = urllib.request.Request(f"{DOMAIN}/oauth2/token", data=body,
                                 headers={"Content-Type": "application/x-www-form-urlencoded"})
    with urllib.request.urlopen(req) as resp:
        return json.load(resp)                      # id_token, access_token, refresh_token

server = http.server.HTTPServer(("localhost", 8080), CallbackHandler)
threading.Thread(target=server.serve_forever, daemon=True).start()
webbrowser.open(f"{DOMAIN}/oauth2/authorize?" + urllib.parse.urlencode({
    "response_type": "code", "client_id": CLIENT_ID, "redirect_uri": REDIRECT_URI,
    "scope": "openid email", "state": state,
    "code_challenge": challenge, "code_challenge_method": "S256"}))
done.wait(timeout=120)                              # wait up to two minutes
server.shutdown()
print(result.get("error") or f"Got tokens: {list(result['tokens'])}")

This sketch skips step 5 (checking the ID token) to stay short; use the checks from "Checking tokens in your API" before trusting the tokens.

The extra route in agent platforms (AgentCore Identity)

When an agent needs a user's approval for an outside service, AgentCore Identity sends the browser to your registered return address with a session_id in the query string (AWS docs). That handler:

  1. Reads session_id; if it is missing, answers with an error (AWS's sample returns HTTP 400).
  2. Finds out who is logged into your app in this browser, from your own session cookie.
  3. If that is the same user the agent was working for, calls CompleteResourceTokenAuth with the session (sessionUri) and the user (userIdentifier, either the user's original login token or their user ID).
  4. If the users differ, does nothing (and may log it), so a leaked approval link cannot attach a stranger's account.

The agent then asks AgentCore for the token again and receives it. Each approval link is valid for 10 minutes, and the return address must be registered as an allowed return URL on the agent's workload identity. For local testing, the AgentCore developer tooling can host this endpoint for you.

In AI agent platforms (for example AgentCore Identity)

When an agent needs access to a service such as Google Drive on a user's behalf, the user must approve it in their browser. The provider sends the browser to the agent platform's own callback, which stores the resulting token. The platform then sends the browser on to your app's callback, so your app can confirm that the person who approved is the same user the agent is working for. That check stops a leaked approval link from attaching a stranger's account. Locally this is the localhost server; in production, a route on your app.

When no callback is needed

If no person is logging in, for example a background service using the client credentials flow, or a service using a fixed API key, there is no browser and no approval screen, so there is nothing to send back and no callback URL is needed.
