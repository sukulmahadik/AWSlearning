Logging out and cancelling tokens

Logging out is harder than logging in, because an access token that has already been handed out keeps working until it expires. You can cancel the refresh token, but your own API may still accept a copied access token for up to its remaining lifetime.

Why access tokens can't simply be switched off

Your API checks a token by verifying its signature with Cognito's public keys. It does not phone Cognito each time; that is what makes tokens fast. The downside: if Cognito cancels a token, your API has no way of knowing, unless you add an extra check.

What actually happens on logout

Action What it does What it does not do
App deletes its stored tokens The app forgets the user, so they look logged out A copy stolen earlier still works until expiry
RevokeToken (cancel a refresh token) The refresh token can no longer get new tokens; Cognito's own APIs also reject access tokens issued from it Your API, checking signatures locally, still accepts those access tokens until they expire
GlobalSignOut Cancels all of the user's refresh tokens, on every device Same limit as above
Visit Cognito's /logout address Clears Cognito's login session cookie, so the login page asks for the password next time Does not sign the user out of Google or their company login

Practical advice

  • Keep access tokens short-lived, for example 5 to 15 minutes. A stolen token then becomes useless quickly, and refresh tokens keep users logged in meanwhile.
  • On logout, do all three: delete tokens in the app, revoke the refresh token, and send the browser to /logout if you use Cognito's login page.
  • If you truly need instant cut-off (for example, a fired employee), keep a short block list of revoked token IDs (jti) or users that your API checks, or call Cognito to check the token for sensitive actions.

Where to keep tokens in a browser or app

Whoever holds a token can act as the user, so where the app stores tokens matters as much as how it gets them. For websites, the safest common pattern is to keep tokens on your server and give the browser only a secure cookie.

The main threat: XSS

Cross-site scripting (XSS) means an attacker manages to run their own JavaScript on your web page, for example through an unsafe third-party script. Any token that page's JavaScript can read, the attacker's script can read too, and send away.

Options for websites

Where How it works Risk Good for
localStorage / sessionStorage Browser storage that JavaScript can read Stolen easily by XSS; localStorage also survives closing the browser Prototypes only
Memory (a JavaScript variable) Kept only while the page is open Still readable by XSS while the page is open; lost on refresh, so users re-login or silently refresh Single-page apps that refresh often
HTTP-only cookie set by your server The browser sends it automatically; JavaScript cannot read it XSS cannot steal it, but needs protection against forged requests (CSRF), e.g. SameSite cookies Most production websites
Backend-for-frontend (BFF) Your server holds the tokens and gives the browser only a session cookie The browser never sees a token at all The most secure option for websites

Mobile and desktop apps

Use the operating system's secure store: Keychain on iPhone and Mac, Keystore on Android, the credential manager on Windows. Never store tokens in plain files or ordinary app settings.

Services and scripts

Keep the client secret in a secrets manager such as AWS Secrets Manager, not in code or in git. Tokens can stay in memory and be fetched again when they expire.

Refresh tokens deserve the most care, because they last longest (30 days by default). Cognito can rotate refresh tokens, issuing a new one each time it is used, so a stolen old one stops working.

Checking tokens in your API: a worked example

Before your API trusts anything in a token, it must confirm six things: the signature is genuine, it came from your User Pool, it has not expired, it is the right kind of token, it was issued to one of your apps, and it carries the permission this endpoint needs. A ready-made library does all of this in a few lines.

The checks, in order

  1. Signature: fetch the User Pool's public keys from https://cognito-idp.<region>.amazonaws.com/<user-pool-id>/.well-known/jwks.json (cache them), pick the key matching the token's kid, and verify.
  2. Issuer (iss): must equal https://cognito-idp.<region>.amazonaws.com/<user-pool-id>.
  3. Expiry (exp): must be in the future.
  4. Kind (token_use): must be access for API calls.
  5. App (client_id): must be one of your app clients.
  6. Permission: the scope claim (or cognito:groups) must include what this endpoint needs.

JavaScript / TypeScript, using AWS's aws-jwt-verify library

import { CognitoJwtVerifier } from "aws-jwt-verify";

const verifier = CognitoJwtVerifier.create({
  userPoolId: "us-east-1_AbC123",
  tokenUse: "access",            // check 4
  clientId: "4abcexampleclientid", // check 5
  scope: "orders-api/read",      // check 6
});

// Checks 1-3 happen inside verify(); it throws if anything is wrong.
const claims = await verifier.verify(tokenFromAuthorizationHeader);
console.log("Request from", claims.sub);

Python, using PyJWT

import jwt
from jwt import PyJWKClient

REGION = "us-east-1"
POOL_ID = "us-east-1_AbC123"
CLIENT_ID = "4abcexampleclientid"
ISSUER = f"https://cognito-idp.{REGION}.amazonaws.com/{POOL_ID}"
jwks = PyJWKClient(f"{ISSUER}/.well-known/jwks.json")  # caches keys

def verify_access_token(token: str, required_scope: str) -> dict:
    signing_key = jwks.get_signing_key_from_jwt(token).key          # check 1
    claims = jwt.decode(
        token, signing_key, algorithms=["RS256"],
        issuer=ISSUER,                                              # check 2
        options={"verify_aud": False},  # access tokens have no 'aud'
    )                                                               # check 3 (exp) is automatic
    if claims.get("token_use") != "access":                        # check 4
        raise PermissionError("not an access token")
    if claims.get("client_id") != CLIENT_ID:                       # check 5
        raise PermissionError("unknown app")
    if required_scope not in claims.get("scope", "").split():      # check 6
        raise PermissionError("missing scope")
    return claims

Where the token comes from: the app sends it in the request header Authorization: Bearer <access token>.

Or let AWS do it: if your API sits behind API Gateway, a Cognito authorizer performs these checks before your code runs (see "Choosing an API Gateway authorizer" below).

Common mistakes

  • Decoding the payload without checking the signature. Anyone can forge an unsigned payload.
  • Accepting ID tokens at the API. They describe the user but are not meant to grant access.
  • Fetching the public keys on every request instead of caching them.
