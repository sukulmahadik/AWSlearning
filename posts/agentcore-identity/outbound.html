Outbound flows: acting for a user, or acting alone

When an agent needs a credential for an outside service, it asks AgentCore Identity with its workload access token, naming the credential provider and the scopes. How AgentCore gets that credential depends on whose data the agent needs.

Flow Also called Who approves Typical use SDK auth_flow value
User federation 3-legged OAuth (3LO), authorization code grant The user, on the provider's consent screen Reading the user's Google Drive, posting to their Slack, creating their Jira tickets USER_FEDERATION
Machine-to-machine 2-legged OAuth (2LO), client credentials grant Nobody; the agent's own client credentials are enough Calling an internal API, a partner API, a shared service account M2M
On-behalf-of token exchange OAuth token exchange The user, implicitly through their existing login Trading the user's inbound token for a token for a downstream API that trusts the same identity provider ON_BEHALF_OF_TOKEN_EXCHANGE
API key — Nobody Services that use a single key, such as weather or search APIs (uses @requires_api_key)

User federation (3LO), step by step

Example: Maya asks the travel agent "what's on my calendar next week?" and the agent needs her Google Calendar.

  1. The agent asks for a token. It calls GetResourceOauth2Token with its workload access token (agent + Maya), the provider name google-provider, the scopes, and the flow USER_FEDERATION. The SDK decorator does this for you.
  2. If the vault already has a valid token for agent + Maya, AgentCore returns it immediately. Skip to step 7.
  3. If the token expired but a refresh token exists, AgentCore refreshes it with Google behind the scenes and returns the new one. Skip to step 7.
  4. Otherwise, AgentCore returns an authorization URL instead of a token. Your agent passes it back to your app (the decorator's on_auth_url callback), and your app shows Maya a "Connect Google Calendar" link.
  5. Maya opens the link and approves on Google's own consent screen. Google sends her browser to AgentCore's callback URL with a code. AgentCore swaps the code for tokens using the Google client secret, and stores them in the vault under agent + Maya.
  6. Session binding. AgentCore sends Maya's browser on to your app's return URL, and your app confirms the person who approved is the user the agent is working for (next section).
  7. The agent receives the access token and calls the Google Calendar API.

Next week, Maya's question gets an answer straight away: the token is still in the vault, or is refreshed silently.

Machine-to-machine (2LO), step by step

Example: a reporting agent pulls figures from your company's internal sales API, which uses Cognito client credentials.

  1. The agent asks for a token with flow M2M, naming the provider (for example a CognitoOauth2 or CustomOauth2 provider for that API) and the scopes it needs.
  2. AgentCore calls the provider's token endpoint with the stored client ID and secret.
  3. The provider returns an access token for the agent itself. No user is involved and no consent screen appears.
  4. The agent calls the API with it. AgentCore can reuse the token until it expires.

Things to know about outbound tokens

  • Tokens can be revoked outside AgentCore. If a user removes the agent's access in their Google account, the stored token stops working and AgentCore cannot know in advance. Handle the API error by asking again with force_authentication=True, which clears the stored token and starts a fresh consent.
  • Ask for the narrowest scopes that do the job, such as drive.metadata.readonly rather than full Drive access. Users see the scopes on the consent screen.
  • Calls to AWS services don't use the vault. If the agent reads S3 or DynamoDB, that goes through its IAM execution role.

Predefined and custom credential providers: who handles the callback

AgentCore Identity offers two kinds of OAuth credential providers. Predefined (built-in) providers, such as GoogleOauth2, GithubOauth2 or SlackOauth2, come with the provider's addresses and provider-specific settings already filled in; you supply only a client ID and secret. A custom provider, CustomOauth2, works with any OAuth 2.0 server, but you must tell AgentCore where that server lives. Either way, AgentCore hosts the OAuth callback: it receives the provider's code, swaps it for tokens and stores them in the vault. Your app's only job is the final session-binding step.

The two kinds side by side

Predefined provider Custom provider (CustomOauth2)
Examples GoogleOauth2, GithubOauth2, SlackOauth2, SalesforceOauth2, MicrosoftOauth2, AtlassianOauth2, FacebookOauth2, CognitoOauth2 and more Your company's OAuth server, Keycloak, a partner API, any provider without a built-in vendor
What you enter Client ID and client secret Client ID, client secret (or another client authentication method), and where the server lives
Where the provider's addresses come from Built into AgentCore A discovery URL ending in /.well-known/openid-configuration or /.well-known/oauth-authorization-server, or the authorization server metadata (issuer, authorization and token endpoints) entered directly
Provider-specific settings Preconfigured by AWS You set what the server needs, for example how the client authenticates at the token endpoint
Callback URL AgentCore's callbackUrl, unique to the provider The same: AgentCore's callbackUrl, unique to the provider
Who handles the callback AgentCore AgentCore
User flow (3LO) and M2M (2LO) Supported where the provider supports them Supported

What "predefined" actually gives you

AWS describes built-in providers as having the authorization server endpoints and provider-specific parameters preconfigured (AWS docs). In practice that means:

  • You don't look up addresses. AgentCore already knows Google's authorization page and token endpoint, GitHub's, Slack's and so on.
  • Provider quirks are handled. Providers differ in small ways, such as how scopes are written, which extra parameters they expect, and how they return tokens. The built-in vendor takes care of these for that provider.
  • Setup is three values: a name for the provider, the client ID and the client secret.

Setting up a custom provider

First register an OAuth client at your provider, then create the AgentCore provider pointing at it. With a discovery URL:

aws bedrock-agentcore-control create-oauth2-credential-provider \
  --name "inventory-api" \
  --credential-provider-vendor "CustomOauth2" \
  --oauth2-provider-config-input '{
      "customOauth2ProviderConfig": {
        "oauthDiscovery": {"discoveryUrl": "https://auth.example.com/.well-known/openid-configuration"},
        "clientId": "<client-id>",
        "clientSecret": "<client-secret>"
      }
    }'

The custom configuration also lets you choose (API reference):

  • oauthDiscovery (required): either discoveryUrl, or authorizationServerMetadata with the server's addresses entered directly, for servers that don't publish a discovery document.
  • clientAuthenticationMethod: how AgentCore proves itself at the token endpoint, such as CLIENT_SECRET_BASIC, CLIENT_SECRET_POST or PRIVATE_KEY_JWT.
  • clientSecretSource: MANAGED (AgentCore stores the secret) or EXTERNAL (a Secrets Manager secret you manage).
  • onBehalfOfTokenExchangeConfig: settings for exchanging a user's token for one the API accepts.
  • Private endpoints: for OAuth servers reachable only inside your network.

Then, exactly as for a predefined provider, copy the returned callbackUrl into your OAuth client's allowed redirect URIs at the provider.

How AgentCore handles the callback, step by step

The callback work is the same for predefined and custom providers; only where the addresses come from differs.

  1. The agent asks for a token (GetResourceOauth2Token) with flow USER_FEDERATION. AgentCore records a pending request for this agent and user, and returns an authorization URL and a session URI.
  2. The authorization URL points at the provider, with AgentCore's client ID there, the requested scopes, a state value and redirect_uri set to the provider's callbackUrl: https://bedrock-agentcore.<region>.amazonaws.com/identities/oauth2/callback/<id>.
  3. The user approves at the provider, which redirects the browser to that callbackUrl with a code.
  4. AgentCore identifies the provider from the callback address. The <id> at the end is unique to one credential provider, so AgentCore knows which configuration and which stored client secret to use.
  5. AgentCore matches the response to the pending request using state, and swaps the code at the provider's token endpoint using the client secret from Secrets Manager (or the configured client authentication method).
  6. AgentCore keeps the tokens for this agent and user, but releases them only after session binding.
  7. AgentCore redirects the browser to your app's return URL with a session_id. Your app checks the logged-in user and calls CompleteResourceTokenAuth (next section).
  8. The agent asks again and receives the access token. Later calls reuse or silently refresh it.

What you build, and what you don't

Callback Who registers it Who implements it
Provider → AgentCore (callbackUrl) You register it at Google, GitHub, Slack or your OAuth server AgentCore, for predefined and custom providers alike
AgentCore → your app (return URL) You register it on the agent's workload identity Your app: confirm the user and call CompleteResourceTokenAuth

For machine-to-machine (M2M) use there is no browser and no callback at all: AgentCore calls the provider's token endpoint directly with the client credentials, for predefined and custom providers alike.

So choosing a predefined or a custom provider changes how much configuration you do, but never adds OAuth callback code to your agent or app: AgentCore always receives the provider's callback, and your app only handles session binding.

Session binding and the callback flow

Session binding is the step where your app confirms that the person who just approved access at Google is the same person the agent is working for. Without it, a leaked authorization link could let a stranger attach their account to someone else's session, or trick a user into attaching theirs to an attacker's.

The problem it prevents

The authorization URL from step 4 of the user federation flow is just a link. If it leaks (copied into a chat, logged, or sent in a phishing email), whoever opens it and approves would have their Google account stored in the vault under Maya's name. The agent would then read the wrong person's data for Maya, or an attacker's data could be planted into Maya's session.

How the flow works (AWS docs)

  1. When the agent asks for a token, AgentCore returns an authorization URL and a session URI identifying this pending request. Each is valid for 10 minutes.
  2. The user opens the URL and approves at the provider.
  3. The provider sends the browser to AgentCore's callback URL. AgentCore swaps the code for tokens but does not release them yet.
  4. AgentCore sends the browser on to your app's return URL, with a session_id in the address.
  5. Your app's handler checks who is logged into your app in this browser (from your own session cookie).
  6. If that is the user the agent was acting for, your app calls CompleteResourceTokenAuth with the session URI and the user's identity (their original login token, or their user ID).
  7. AgentCore now releases the token into the vault for that agent and user. The next time the agent asks, it receives it.

If the users don't match, your app does nothing (and can log the attempt), so the token is never bound.

What you need to set up

  • A return URL route in your app, such as https://app.example.com/oauth/return. It reads session_id, checks the logged-in user, and calls CompleteResourceTokenAuth. If session_id is missing it should return an error.
  • Register that URL as an allowed OAuth return URL on the agent's workload identity (CreateWorkloadIdentity or UpdateWorkloadIdentity). AgentCore only redirects to registered addresses.
  • Pass it to the decorator as callback_url, or let the runtime supply it.
  • For local testing, a small local callback server plays this role; AWS's samples include one, and the AgentCore developer tooling can host the endpoint for you.

Two callback URLs, two jobs

URL Owned by Registered at Purpose
AgentCore's callbackUrl AgentCore Identity The provider (Google, GitHub, Slack) as a redirect URI Receives the provider's code and swaps it for tokens
Your app's return URL Your app The agent's workload identity, as an allowed return URL Confirms the right user and calls CompleteResourceTokenAuth

Use state too. Pass an unguessable custom_state value when requesting the token and check it comes back unchanged, as extra protection against forged requests.

The consent portal option. If your agent's tools sit behind an AgentCore Gateway with JWT inbound auth, AWS can host a consent portal for you: an AWS-managed page that signs users in through your OpenID Connect provider and collects their consent, keeping the whole OAuth exchange on the server side so the browser never holds a token (AWS docs).
