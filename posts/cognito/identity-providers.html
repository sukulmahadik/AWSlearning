How a User Pool works with other identity providers

A User Pool is an identity provider in its own right, and it can also pass the job of checking passwords to other providers such as Google or a company login. Either way, your app receives the same kind of Cognito tokens.

Why this matters

Users often prefer "Sign in with Google" over creating yet another password. Companies want employees to use their existing work login. Federation lets the User Pool accept both, while your app only has to understand one kind of token: Cognito's.

Kinds of providers a User Pool can connect to

Kind Examples In plain terms
The User Pool itself Username and password stored in Cognito Users create an account directly in your app
Social providers Google, Apple, Facebook, Login with Amazon Users sign in with a personal account they already have
Company providers using SAML Microsoft Entra ID, ADFS, Okta, Ping Employees sign in with their work account. SAML is an older, XML-based standard common in large companies
Any OIDC provider Auth0, Okta, Salesforce Any service that follows the OpenID Connect standard

What happens when a user picks "Sign in with Google"

  1. The User Pool sends the user to Google's login page.
  2. Google checks the password. Cognito never sees the Google password.
  3. Google sends the user back to the User Pool with proof of who they are.
  4. The User Pool copies useful details (email, name) from Google's proof into its own user record. This copying is called attribute mapping, and you choose which details to copy.
  5. The User Pool creates a user record for this person (a federated user, with a username like Google_1098...), or links it to an existing account with the same email if you set that up.
  6. The User Pool issues its own tokens to your app. Inside the ID token, a claim called identities records that this user came through Google.

Each application registered with the User Pool can choose which providers to offer. An internal admin app might allow only the company login, while a customer app offers Google and Apple.

How identity providers trust each other

Identity providers can be chained together: one provider accepts another provider's proof, then issues its own proof to the next system. Each system only has to trust its immediate neighbour, not everyone in the chain.

An everyday comparison

Your employer confirms your identity to a travel agency. The travel agency issues you a ticket. The airline checks only the ticket; it never calls your employer. Each step trusts the one before it and issues something new.

Key ideas

  • Trust goes one way. When a User Pool trusts Google, it accepts Google's word about users. Google knows nothing about your app and does not trust the User Pool back.
  • A broker sits in the middle. Some services act as go-betweens. Cognito User Pools, Okta, Auth0 and Entra ID can all do this. Toward the provider above them, they behave like an ordinary app asking for a login. Toward the app below them, they behave like an identity provider handing out tokens.
  • Chains can have several links. A realistic example:
    1. An employee logs in with their company's Entra ID.
    2. Entra ID sends proof to the Cognito User Pool.
    3. The User Pool issues its own token to the app.
    4. The app hands that token to an Identity Pool.
    5. The Identity Pool gets AWS credentials from STS. At every hop, the receiver checks the previous proof's signature before issuing its own.
  • The format can change along the way. A company provider may speak SAML, while the User Pool hands out JWTs. The broker translates between them.
  • The Identity Pool only receives. It trusts identity providers (including User Pools), but it does not issue identity tokens; it issues AWS credentials.
  • One person, several logins. If the same person sometimes uses Google and sometimes Facebook, both logins can be linked to one user record, so their data stays the same either way.

Rule of thumb: let your app trust as few providers as possible, ideally just one broker such as a Cognito User Pool, and let the broker handle every other provider.

The confusing part: two sets of client IDs

When you add "Sign in with Google" to a User Pool, you end up with two different client IDs, because there are two separate relationships: your app is a customer of Cognito, and Cognito is a customer of Google.

Why two?

Remember the broker idea from earlier. Cognito sits in the middle:

  • Looking down toward your app, Cognito is the login provider. Your app must be registered with Cognito, so your app gets a client ID from Cognito.
  • Looking up toward Google, Cognito is just another app asking Google to log someone in. So Cognito must be registered with Google, and gets a client ID from Google.
Registration 1 Registration 2
Who is asking for logins (the client) Your app Cognito
Who provides the logins (the server) Cognito Google
Where you create it Cognito console → your User Pool → App clients Google Cloud Console → Credentials → OAuth client
Where the values end up In your app's configuration Pasted into the User Pool's Google provider settings
"Send the user back to" URL Your app's address, e.g. https://app.example.com/callback Cognito's address, ending in /oauth2/idpresponse

Your app never sees Google's client ID or secret, and never talks to Google directly. Adding Apple or a company login later repeats the pattern: one registration at that provider, for Cognito.

The whole journey, step by step

  1. The user clicks Login in your app. The app sends the browser to Cognito, including your app's client ID so Cognito knows which app this is.
  2. Cognito shows its login page with the buttons allowed for that app. The user clicks Sign in with Google.
  3. Cognito sends the browser to Google, this time including Cognito's Google client ID, so Google knows Cognito is asking.
  4. The user types their Google password on Google's own page. Google sends the browser back to Cognito with a one-time code.
  5. Behind the scenes, Cognito swaps that code with Google for proof of the user's identity, using its Google client secret.
  6. Cognito creates or finds the user in the User Pool and sends the browser back to your app with a new one-time code of its own.
  7. Your app's server swaps that code with Cognito for tokens, using your app's client ID and secret (or PKCE).
  8. The user is now logged in. If needed, the app can take the ID token to an Identity Pool to get AWS access.

Two ways to bring in Google (or any IdP)

Google can be connected to the User Pool or directly to the Identity Pool. Connecting through the User Pool is the usual choice; connecting directly is simpler but gives you less.

Option A: Google → User Pool → Identity Pool

Google is added as a login option on the User Pool, exactly as described in the previous section. The Identity Pool trusts only the User Pool.

  • The user can sign in with Google, or with any other option you allow.
  • Your app always ends up holding Cognito tokens, no matter which button was clicked.
  • If the app needs AWS access, it takes the Cognito ID token to the Identity Pool.

Option B: Google → Identity Pool directly

There is no User Pool at all. Your app shows Google's own sign-in button, gets a token from Google, and hands that Google token straight to the Identity Pool, which trusts Google directly. In code, the app passes it in a field called Logins, for example {"accounts.google.com": "<google-token>"}.

Comparing the two

A: through the User Pool B: directly to the Identity Pool
You keep your own list of users Yes No
Tokens your own API can check Yes, always the same Cognito format No, only Google's tokens
Can use groups to decide permissions Yes No, only what Google's token contains
Ready-made login page, MFA, custom steps Yes No, you build the login yourself
Setup effort Higher Lower
Good fit for Apps with their own backend API and real user management Small mobile or IoT apps that only need to reach AWS

The same choice exists for company logins (SAML or OIDC). Option A is the common default, because your API only ever has to understand one kind of token.

Google, Facebook and other providers: the credentials behind the buttons

When you add "Sign in with Google" to Cognito, or let an agent read a user's Google Drive through AgentCore Identity, Google treats Cognito or AgentCore as an app of its own. You register that app with Google, and Google gives you a client ID and client secret that you hand to Cognito or AgentCore. The same is true for Facebook, Apple, GitHub and the rest.

Why the providers issue credentials at all

Google will not hand a user's identity, or access to their data, to an unknown caller. Every app that asks Google to log someone in must first be registered, so Google knows:

  • who is asking (the client ID, shown to the user on the consent screen as your app's name),
  • that the request really comes from that app (the client secret, used on the back channel),
  • where it may send the user back (the registered redirect URI), and
  • what the app may ask for (the scopes on the consent screen).

Cognito and AgentCore both run on AWS servers, so they are confidential clients of Google: they can keep the secret safe and use it when swapping Google's authorization code for tokens.

Part 1: Cognito and social providers (logging users in)

Here the goal is identity only: "this person is maya@gmail.com". The User Pool is Google's client, and your app never talks to Google.

What each provider gives you, and where it goes in Cognito

Provider Where you register What you get What you enter in the User Pool Typical scopes
Google Google Cloud Console → Credentials → OAuth client ID (type: Web application) Client ID and client secret Google client ID, client secret, authorized scopes openid email profile
Facebook Meta for Developers → create an app → Facebook Login App ID and app secret App ID, app secret, authorized scopes, Graph API version public_profile,email
Apple Apple Developer → a Services ID plus a Sign in with Apple key Services ID, Team ID, Key ID and a private key file (.p8), not a fixed secret Services ID, Team ID, Key ID, private key email name
Login with Amazon Amazon Developer Console → security profile Client ID and client secret Client ID, client secret, scopes profile
Any OIDC provider (Okta, Auth0, Entra ID in OIDC mode) That provider's admin console → new app registration Client ID, client secret, issuer URL Client ID, client secret, issuer URL, scopes openid email profile
SAML providers (Entra ID, ADFS, Okta in SAML mode) That provider's admin console → new enterprise app No client ID or secret; a metadata file with certificates instead The metadata file or its URL Not used; attributes come in the SAML assertion

Setting up Google, step by step

  1. Give the User Pool a domain, such as https://my-app.auth.us-east-1.amazoncognito.com. Google will send users back here.
  2. In Google Cloud Console, configure the OAuth consent screen (app name, support email, authorized domain amazoncognito.com), then create an OAuth client ID of type Web application.
  3. Register Cognito's addresses at Google: authorized JavaScript origin https://my-app.auth.us-east-1.amazoncognito.com, and authorized redirect URI https://my-app.auth.us-east-1.amazoncognito.com/oauth2/idpresponse.
  4. Copy Google's client ID and client secret.
  5. In the User Pool, add Google as an identity provider: paste the client ID and secret, set authorized scopes to openid email profile.
  6. Map attributes: Google's email → email, name → name, picture → picture. Google's sub becomes the federated username (Google_1098…).
  7. Enable Google on each app client that should show the button.

Facebook follows the same pattern: the redirect URI registered in Meta for Developers is the same Cognito /oauth2/idpresponse address, and the App ID and app secret go into the User Pool.

What happens at login, and where each credential is used

  1. Your app sends the browser to Cognito with your app's client ID (from the User Pool).
  2. Cognito sends the browser to Google with Cognito's Google client ID.
  3. The user signs in at Google and approves. Google sends the browser back to Cognito's /oauth2/idpresponse with a code.
  4. Cognito's servers call Google's token endpoint with the code plus Cognito's Google client ID and client secret. This is the only place Google's secret is ever used.
  5. Cognito reads who the user is: from Google's ID token (Google speaks OpenID Connect), or for Facebook, which is plain OAuth rather than OpenID Connect, by calling Facebook's Graph API with the access token it just received.
  6. Cognito creates or updates the federated user, then issues its own tokens to your app.

Google's and Facebook's own tokens stay inside Cognito. Your app receives only Cognito tokens. If you need the user's Google data later, this login does not give you a usable Google token; that is AgentCore's job (Part 2).

When the Identity Pool trusts Google directly

In the "direct to Identity Pool" option, your app runs Google Sign-In itself, using its own Google client ID (often an Android or iOS client type with no secret). The Identity Pool is configured with that Google client ID only, and checks that Google's ID token was issued for it (the token's audience). It needs no secret, because it never swaps a code with Google; it only verifies a token the app already has.

Looking after the provider credentials

  • Treat Google's client secret and Facebook's app secret like passwords. They are stored in the User Pool's provider settings, not in your app.
  • To rotate one, create a new secret at the provider, update it in the User Pool's identity provider settings, then delete the old secret at the provider.
  • If you change the User Pool's domain, update the redirect URI at every provider, or their logins break.
  • Google and Facebook may require app review or verification before showing your consent screen to the public, especially for sensitive scopes.

Part 2: AgentCore Identity and the same providers (acting for users)

AgentCore Identity uses Google and Facebook for a different purpose: not to find out who the user is, but to let an agent call the provider's APIs on the user's behalf, for example reading their Google Drive or Calendar.

Inbound and outbound, again

  • Inbound (who may call the agent): AgentCore checks a JWT from an identity provider you configure, typically a Cognito User Pool, Okta, Entra ID or Auth0. If users sign in with Google, the usual pattern is Google → Cognito → your app → agent: Cognito federates Google exactly as in Part 1, and AgentCore trusts Cognito's tokens. Google is documented as an outbound provider for AgentCore, not an inbound one.
  • Outbound (what the agent may reach): this is where Google and Facebook register AgentCore as an app and give it credentials.

Registering AgentCore with Google, step by step (AWS docs)

  1. In Google Cloud Console, configure the OAuth consent screen. Add bedrock-agentcore.<region>.amazonaws.com as an authorized domain, and add the API scopes the agent needs, such as https://www.googleapis.com/auth/drive.readonly.
  2. Create an OAuth client ID and copy its client ID and client secret. Leave the redirect URIs empty for now.
  3. Create a credential provider in AgentCore with CreateOauth2CredentialProvider: vendor GoogleOauth2, plus the client ID and client secret. AgentCore stores the secret in AWS Secrets Manager.
  4. AgentCore returns a callbackUrl, unique to this provider, such as https://bedrock-agentcore.us-east-1.amazonaws.com/identities/oauth2/callback/<id>.
  5. Go back to Google and add that callbackUrl as an authorized redirect URI.

Facebook works the same way with the FacebookOauth2 vendor, using the App ID and app secret from Meta for Developers. AgentCore has built-in vendors for many providers, including Google, Facebook, GitHub, Slack, Salesforce, Microsoft, Atlassian, Okta and Cognito itself, and a CustomOauth2 vendor for any other OAuth 2.0 provider (API reference).

What happens when the agent needs a user's Google Drive

  1. The agent asks AgentCore for a Google token for this user (GetResourceOauth2Token, naming the credential provider and the scopes).
  2. If the token vault already holds a valid token for this user, AgentCore returns it. Done.
  3. If not, AgentCore returns an authorization URL. The user opens it and approves access at Google.
  4. Google redirects to AgentCore's callbackUrl with a code. AgentCore swaps it at Google's token endpoint using its own Google client ID and secret, and stores the resulting access and refresh tokens in the vault, tied to this user.
  5. AgentCore then sends the browser to your app's return URL so your app can confirm the user who approved is the right one (the session binding step described in the callback section).
  6. The agent asks again, receives the Google access token, and calls the Drive API.

AgentCore also supports a machine-to-machine flow (client credentials) for providers where the agent acts as itself rather than for a user.

Putting the two together: three separate registrations

A full system where users sign in with Google and an agent reads their Drive involves three different client registrations:

# Client Registered with Credentials Redirect URI Purpose Scopes
1 Your app Cognito User Pool (app client) Your app's client ID (+ secret or PKCE) Your app's /callback Users log into your app openid email + custom API scopes
2 Cognito Google Cloud Console Google client ID + secret (for Cognito) Cognito's /oauth2/idpresponse Google confirms who the user is openid email profile
3 AgentCore Identity Google Cloud Console Google client ID + secret (for AgentCore) AgentCore's callbackUrl Agent calls Google APIs for the user e.g. drive.readonly

Registrations 2 and 3 can live in the same Google Cloud project, but they are separate OAuth clients: different redirect URIs, different scopes and different reasons to show the user a consent screen. Keeping them separate also means a leaked or rotated secret affects only one of them.

In one sentence: Google and Facebook give Cognito credentials so it can ask them who the user is, and give AgentCore Identity credentials so it can ask them for access to the user's data; your app holds neither secret.
