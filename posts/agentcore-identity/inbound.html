Before an agent hosted in AgentCore Runtime does any work, the runtime checks the caller. You choose one of two methods per runtime: IAM (SigV4), the default, or a JWT bearer token from an identity provider you trust. A runtime uses one or the other, not both; you can create separate runtime versions if you need each (AWS docs).

Option 1: IAM (SigV4), the default

The caller signs the request with AWS credentials, exactly like any other AWS API call, and IAM decides whether it may call bedrock-agentcore:InvokeAgentRuntime on this runtime.

  • Best for: your own backend services, Lambda functions, Step Functions and other AWS workloads calling the agent.
  • No extra setup: it works out of the box.
  • Knowing the user: an IAM caller is a service, not a person. If the agent must act for a specific user, the caller can pass the user's ID in the X-Amzn-Bedrock-AgentCore-Runtime-User-Id header. That needs the extra permission bedrock-agentcore:InvokeAgentRuntimeForUser.
  • Caution: AgentCore treats that header as an unverified label. Only trusted callers should hold that permission, and they should take the user ID from an authenticated source, never from free-form input. AWS recommends JWT authentication instead for production apps with real end users.

Option 2: JWT bearer token (OAuth)

The caller sends Authorization: Bearer <token>, where the token is a JWT issued by an identity provider such as a Cognito User Pool, Okta, Entra ID or Auth0. The runtime's inbound JWT authorizer checks it before your code runs.

What you configure

Setting Checked against Example
Discovery URL The token's issuer (iss) and signing keys https://cognito-idp.us-east-1.amazonaws.com/us-east-1_AbC123/.well-known/openid-configuration
Allowed clients The token's client_id claim Your web app's Cognito app client ID
Allowed audiences The token's aud claim orders-agent
Allowed scopes The token's scope claim agents/invoke
Required custom claims Named claims and values in the token tenant_tier = premium

If you set both allowed clients and allowed audiences, both are checked. The discovery URL must end in /.well-known/openid-configuration; the authorizer fetches the provider's public keys from it to verify signatures.

What happens on each call

  1. The user signs in to your app through the identity provider. The app receives a JWT.
  2. The app calls the agent's endpoint with Authorization: Bearer <JWT>.
  3. The runtime checks the signature, expiry, issuer, and any client, audience, scope or claim rules.
  4. If anything fails, the caller gets 401 Unauthorized, with a WWW-Authenticate header pointing to metadata that tells clients which authorization server to use.
  5. If it passes, the runtime takes the user's identity from the token (iss and sub), creates a workload access token for "this agent, acting for this user", and runs your code with it.

Reading the user's claims in your code (optional). By default your code doesn't receive the raw Authorization header. Add it to the runtime's request header allow-list if your code needs claims such as the user's email or tenant; the token has already been verified, so your code can simply decode it.

Which should you choose?

Situation Use
A web or mobile app with signed-in users calls the agent JWT bearer token
An MCP client or partner system with its own OAuth server JWT bearer token
Your own AWS services call the agent, with no end user IAM (SigV4)
An AWS service calls on behalf of users your system has already authenticated IAM + the user ID header, tightly restricted
Quick local tests IAM, or the user ID header, before an identity provider exists

Putting a gateway in front. You can make AgentCore Gateway the only entry point to a runtime, for central policies, guardrails and logging. With IAM inbound auth, add a resource policy that allows only the gateway's role; with JWT inbound auth, use the authorizer's allowedWorkloadConfiguration to accept calls only when the gateway is in the request's identity chain.
