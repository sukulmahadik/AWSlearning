Local development vs AgentCore Runtime

The same decorators work on your laptop and in AgentCore Runtime. What changes is who supplies the workload access token and who receives the consent link.

On your laptop In AgentCore Runtime Self-hosted (ECS, EKS, Lambda, elsewhere)
Workload identity One you create, or one the AgentCore tooling creates for local runs Created automatically for the runtime One you create with CreateWorkloadIdentity
Workload access token Fetched by the SDK, usually with a test user ID Created by the runtime from the caller's JWT (or user ID header) and passed in the WorkloadAccessToken header Your code calls GetWorkloadAccessTokenForJWT
Who is "the user" A test ID you choose The verified caller The user from your app's login token
Consent link Printed to the console; you open it yourself Streamed back to your app to show the user Sent back through your app
Session binding return URL A local callback server on localhost A route on your real app A route on your real app
AWS credentials for the SDK Your own AWS profile The runtime's execution role and service-linked role That platform's IAM role

A typical development path

  1. Prototype locally with a test user ID and on_auth_url=print. Approve the consent yourself in the browser. A local callback server (or the AgentCore developer tooling) completes session binding on localhost.
  2. Add an identity provider. Create a Cognito User Pool (or use Okta, Entra ID) and get a real JWT for a test user.
  3. Deploy to Runtime with JWT inbound auth (agentcore deploy, or CreateAgentRuntime with an authorizer configuration). Call the agent with Authorization: Bearer <JWT>.
  4. Wire up the consent experience: stream the authorization URL to your app, add the return URL route, register it on the workload identity, and call CompleteResourceTokenAuth.
  5. Lock down: deny the user ID path where it isn't needed, restrict who may invoke the runtime, and put a gateway in front if several agents share tools.

Gotcha: local tokens are not production tokens. Tokens stored while testing with a made-up user ID are tied to that ID. When you switch to real JWT-based users, each real user approves access once.

Security practices and common mistakes

AgentCore Identity removes the biggest risk, secrets in agent code, but a few settings still decide how safe the system is.

Do

  • Use JWT inbound auth for real users. It proves who the user is cryptographically; the user ID header only trusts whoever sets it.
  • Restrict the unverified paths. Grant InvokeAgentRuntimeForUser and GetWorkloadAccessTokenForUserId only to specific trusted roles and resources, and explicitly deny them where they aren't needed.
  • Ask for the narrowest scopes for each tool, such as read-only scopes, and request write scopes only in the tools that write.
  • Implement session binding properly: check the logged-in user before calling CompleteResourceTokenAuth, and use custom_state.
  • Register exact return URLs on the workload identity, and exact callback URLs at each provider.
  • Keep the authorizer tight: set allowed clients or audiences, not just the discovery URL, so tokens issued for other apps by the same identity provider are rejected.
  • Use a customer-managed KMS key for the vault if your compliance rules require control over encryption keys.
  • Monitor with CloudTrail: watch token requests, especially unexpected user IDs or spikes for one provider.
  • Front shared tools with a gateway, and make the gateway the only way in.

Common mistakes

Mistake What goes wrong Fix
Passing client-supplied user IDs One user can pass another's ID and receive their tokens Take the user ID from a verified token or trusted system only
Skipping session binding A leaked consent link can attach the wrong account Implement the return URL route and CompleteResourceTokenAuth
Discovery URL only, no allowed clients Any token from that identity provider passes, including other apps' Add allowed clients and audiences
Printing the consent URL in production Users never see it; the agent waits forever Stream it back to the app
Forgetting the provider's redirect URI Google or GitHub shows a "redirect URI mismatch" error Add AgentCore's callbackUrl at the provider
Treating a stored token as always valid Users can revoke access at the provider Catch 401 errors and retry with force_authentication=True
Putting secrets in prompts or tool descriptions The model can repeat them Keep every secret in a credential provider
One provider for everything, broad scopes A single compromised agent reaches everything One provider per service and purpose, minimal scopes
