Start here: the basic ideas in plain words

Amazon Bedrock AgentCore Identity is the AWS service that answers three questions for an AI agent: who may call it, who the agent itself is, and which outside services it may use, for which user. Everything else in this guide builds on the ten ideas below.

1. Agent

An AI agent is a program that uses a language model to decide what to do, then takes actions by calling tools: an API, a database query, a function. "Summarize my unread email and put the action items in Jira" is a job for an agent: it reads Gmail, thinks, then writes to Jira.

2. Tool

A tool is anything the agent can call to act in the world: a Lambda function, a REST API, a Google Drive API, an MCP server (a standard way to package tools for agents). Most useful tools need credentials before they will answer.

3. Authentication and authorization

  • Authentication proves who is making a request.
  • Authorization decides what they may do.

Agents need both twice over: once when someone calls the agent, and again every time the agent calls a tool.

4. Inbound and outbound

AgentCore Identity splits the problem in two directions:

  • Inbound auth answers "who may call this agent?" It checks the caller's credentials before the agent runs.
  • Outbound auth answers "what may this agent reach?" It supplies the right credential when the agent calls Google, GitHub, Slack or your own API.

5. Workload identity

A workload is any piece of software that runs on its own: a service, a job, an agent. A workload identity is an identity for that software, the way a user account is an identity for a person. In AgentCore, every agent (and every gateway) gets one, so the agent can prove it is the one asking.

6. Token

A token is a short-lived digital pass. Instead of sending a password with every request, a program sends a token that says who it is and what it may do. A JWT (JSON Web Token) is a common token format: readable, signed, and checkable without calling the issuer.

7. OAuth 2.0 and the "legged" flows

OAuth 2.0 is the standard way for an app to get a token to use someone's account without ever seeing their password. Agents mostly use two OAuth flows:

  • 3-legged OAuth (3LO), the authorization code flow: three parties are involved (the user, the agent, and the provider such as Google). The user sees a consent screen and approves. Used when the agent acts for a user, for example reading your Google Drive.
  • 2-legged OAuth (2LO), the client credentials flow, also called machine-to-machine (M2M): only two parties, the agent and the provider. No user and no consent screen. Used when the agent acts as itself, for example calling an internal inventory API.

8. API key

A single secret string that a service gives you to call its API, such as a weather or search API. Simpler than OAuth, but anyone holding the key can use it, so it must be stored safely.

9. Token vault

AgentCore Identity's secure store for tokens and API keys. It remembers, for example, "this agent may use this Google token for this user", so the user doesn't have to approve again on every request, and the secret never sits in the agent's code.

10. Credential provider

A configuration in AgentCore Identity that describes how to get credentials for one outside service: which provider (Google, GitHub, Slack, a custom OAuth server, an API key), and the client ID and secret AWS should use with it.

The big picture

AgentCore Identity sits on both sides of your agent. On the way in, it checks that whoever calls the agent is allowed to. On the way out, it hands the agent the right credential for each outside service, for the right user, without the agent ever storing a secret.

An analogy: a personal assistant in an office building

  1. The front door (inbound). Visitors (callers) must show a badge from an approved issuer before they can talk to the assistant. That badge is the login token from Cognito, Okta or Entra ID.
  2. The assistant's own staff card (workload identity). The assistant has an ID of its own, so the building knows which assistant is acting, separate from the visitor it is helping.
  3. The key safe (token vault). Keys to outside places, such as a client's office (Google Drive) or a supplier's warehouse (GitHub), hang in a locked safe. Each key is labelled with the assistant and the client it belongs to. The assistant can only take a key with both its own staff card and that client's say-so.
  4. The key-cutting service (credential providers). When there is no key yet, the service phones the outside place, gets the client's permission (a consent screen), cuts a key and hangs it in the safe for next time.

Who does what

Piece Plain-English job Example
Identity provider Signs the user in and issues a login token Cognito User Pool, Okta, Entra ID, Auth0
Inbound authorizer Checks the caller's token before the agent runs Accept only tokens from this Cognito pool, for this app client
Workload identity The agent's own identity arn:aws:bedrock-agentcore:…:workload-identity-directory/default/workload-identity/travel-agent
Workload access token A short-lived token meaning "this agent, acting for this user" Created automatically by AgentCore Runtime for each call
Credential provider How to get credentials for one outside service google-provider using Google's client ID and secret
Token vault Stores tokens and keys per agent and per user Maya's Google Drive token for travel-agent
AgentCore SDK decorators Fetch the right credential inside your code with one line @requires_access_token(provider_name="google-provider", …)
