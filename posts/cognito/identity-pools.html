Identity Pools in depth: from a login to AWS credentials

An Identity Pool turns "this person has logged in" into "this person may call these AWS services directly, for the next hour". It does not store users or check passwords. It trusts identity providers you name, gives each person a stable identity ID, picks an IAM role for them, and hands back temporary AWS credentials for that role.

Its official name is Amazon Cognito Federated Identities, and in the AWS SDKs its API is called cognito-identity (User Pools are cognito-idp).

Why Identity Pools exist

User Pool tokens are understood by your API. AWS services such as S3, DynamoDB or AWS IoT only accept requests signed with AWS credentials under IAM. Without an Identity Pool, a mobile app that wants to upload a photo to S3 must send it through a server you run. With one, the app can upload directly, and IAM limits it to that user's own folder.

Without an Identity Pool With an Identity Pool
App → your API → your server's IAM role → S3 App → S3 directly, with the user's own temporary credentials
You run and pay for a server in the middle No server in the data path
Your code enforces per-user rules IAM policies enforce per-user rules

The parts of an Identity Pool

Part What it is Example
Identity pool ID The pool's unique ID, which the app needs us-east-1:1a2b3c4d-1111-2222-3333-444455556666
Identity providers The sources it trusts, each with the ID it must check tokens against A User Pool and its app client ID; Google with your app's Google client ID
Identity ID A permanent ID per person, created on first use us-east-1:9f8e7d6c-aaaa-bbbb-cccc-ddddeeeeffff
Authenticated role The IAM role for signed-in users PhotoAppUserRole
Unauthenticated role (optional) The IAM role for guests, if guest access is switched on PhotoAppGuestRole
Role rules (optional) How to pick different roles for different users Users in group admin get PhotoAppAdminRole
Attributes for access control (optional) Which token claims become session tags for IAM policies department → tag department

Providers it can trust, and how the app names them

The app sends its tokens in a Logins map. The key says which provider the token came from; the value is the token itself.

Provider Key in the Logins map Token the app sends
Cognito User Pool cognito-idp.<region>.amazonaws.com/<user-pool-id> The User Pool ID token
Google accounts.google.com Google's ID token
Facebook graph.facebook.com Facebook's access token
Sign in with Apple appleid.apple.com Apple's ID token
Login with Amazon www.amazon.com Amazon's access token
Any OIDC provider The provider's issuer host, e.g. login.example.com Its ID token (the provider must be registered in IAM first)
SAML provider The ARN of the SAML provider registered in IAM The SAML assertion
Your own login system (developer-authenticated identities) A developer provider name you choose A token your backend gets from Cognito on the user's behalf

For a User Pool, you register the pool and its app client ID. The Identity Pool accepts only ID tokens issued to that app client. You can also switch on a server-side token check, so Cognito confirms the user still exists and their tokens have not been revoked before issuing credentials.

How an app gets credentials, step by step

  1. The user signs in with their provider, for example the User Pool, and the app receives an ID token.
  2. GetId: the app sends the identity pool ID and the Logins map. Cognito checks the token and returns the user's identity ID, creating one on first use.
  3. GetCredentialsForIdentity: the app sends the identity ID and the same Logins map. Cognito picks the IAM role, asks AWS STS for credentials, and returns them.
  4. The app receives an access key ID, a secret key, a session token and an expiry time, typically one hour away.
  5. The app calls AWS directly, for example s3:PutObject, signing each request with those credentials. IAM checks every call against the role's policies.
  6. Before expiry, the app repeats steps 3 to 4, refreshing its User Pool tokens first if needed. AWS SDKs do this automatically.

This is the enhanced (simplified) flow, and it is the one to use. There is also an older basic (classic) flow, where the app gets an OpenID token from Cognito with GetOpenIdToken and calls STS AssumeRoleWithWebIdentity itself, naming the role. It is switched off by default; leave it off unless you have a specific reason.

Python (boto3)

import boto3

REGION = "us-east-1"
IDENTITY_POOL_ID = "us-east-1:1a2b3c4d-1111-2222-3333-444455556666"
logins = {"cognito-idp.us-east-1.amazonaws.com/us-east-1_AbC123": id_token}  # User Pool ID token

identity = boto3.client("cognito-identity", region_name=REGION)
identity_id = identity.get_id(IdentityPoolId=IDENTITY_POOL_ID, Logins=logins)["IdentityId"]
creds = identity.get_credentials_for_identity(IdentityId=identity_id, Logins=logins)["Credentials"]

s3 = boto3.client("s3", region_name=REGION,
                  aws_access_key_id=creds["AccessKeyId"],
                  aws_secret_access_key=creds["SecretKey"],
                  aws_session_token=creds["SessionToken"])
s3.put_object(Bucket="my-photo-bucket", Key=f"users/{identity_id}/photo.jpg", Body=photo_bytes)

JavaScript (AWS SDK v3), where the credential provider handles both calls and refreshes for you:

import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { fromCognitoIdentityPool } from "@aws-sdk/credential-providers";

const s3 = new S3Client({
  region: "us-east-1",
  credentials: fromCognitoIdentityPool({
    clientConfig: { region: "us-east-1" },
    identityPoolId: "us-east-1:1a2b3c4d-1111-2222-3333-444455556666",
    logins: { "cognito-idp.us-east-1.amazonaws.com/us-east-1_AbC123": idToken },
  }),
});

Identity IDs: one per person, kept across logins

  • An identity ID is created the first time a person comes through the pool, and stays the same every time after. It is the natural key for per-user storage, such as s3://my-photo-bucket/users/<identity-id>/.
  • It is not the same as the User Pool's sub. Store the mapping if your backend needs both.
  • Linking: if the app sends tokens from two providers together, say Google and Facebook, both are tied to one identity ID, so the person sees the same data either way.
  • Guests who sign up: a guest has an unauthenticated identity ID. When they sign in, the app can pass that existing ID along with their new login, so their guest data carries over.
  • Identity IDs are per pool and per region. A second Identity Pool gives the same person a different ID.

Guest access (unauthenticated identities)

Switching on guest access lets visitors who have not signed in get very limited AWS credentials, for example to send analytics events or load a map.

  • Guests receive the unauthenticated role. Give it the smallest possible permissions; anyone on the internet can obtain them.
  • In the enhanced flow, Cognito also narrows guest credentials to a fixed list of services, as a safety net.
  • Common uses: Amazon CloudWatch RUM (front-end monitoring), Amazon Location Service maps, sending events to Kinesis or Pinpoint.
  • Never let the guest role read other users' data or write anything costly. Watch for abuse such as someone generating huge numbers of identities.

Choosing roles and limiting access

The Identity Pool decides the role; IAM decides what the role allows. The next section, "IAM roles and Identity Pools", covers the details: default, token-based and rule-based role selection, the trust policy every role needs, the ${cognito-identity.amazonaws.com:sub} policy variable for per-user folders, and attribute-based access control with session tags.

When to use an Identity Pool, and when not to

Good fits

  • Mobile or web apps that upload or download user files directly to and from S3.
  • IoT devices and companion apps connecting to AWS IoT Core.
  • Front-end apps using AWS services built for direct browser use, such as Location Service maps or CloudWatch RUM.
  • Giving users of a company identity provider (SAML) AWS credentials for a specific tool.

Prefer your own API instead when

  • Access rules are complex or depend on business data, which is easier to express in code than in IAM policies.
  • You would have to give users broad permissions, such as querying a whole DynamoDB table.
  • You want one place to log, rate-limit and audit what users do.

Common mistakes

  • Sending the access token instead of the ID token. For a User Pool provider, the Identity Pool needs the ID token.
  • Mismatched app client ID. The app client ID registered on the Identity Pool must match the aud of the ID token the app sends.
  • Roles that are too broad, such as s3:* on a whole bucket. Always scope to the user's own prefix with the policy variable.
  • Trust policies without conditions. Without the aud and amr conditions, other Identity Pools could assume your role.
  • Region mismatch. The identity pool ID starts with its region; the SDK client must use that region.

Cost

Identity Pools themselves have no extra charge. You pay for the AWS services the credentials are used on, and for the User Pool if you use one.

IAM roles and Identity Pools

An Identity Pool has no permissions of its own. Its job is to pick an IAM role for each user and get temporary credentials for it, so the role's rules decide exactly what the user can do in AWS.

A quick refresher on IAM roles

  • An IAM policy is a written rule, such as "allow reading files from the bucket my-photos".
  • An IAM role is a named bundle of policies, for example PhotoAppUserRole.
  • A role is not tied to one person. Anyone the role trusts can borrow it for a limited time. Borrowing a role is called assuming it.
  • The role's trust policy says who is allowed to borrow it. Its permission policies say what the borrower can do.

What happens when a user asks the Identity Pool for access

  1. The app sends the user's token (from the User Pool, Google, and so on).
  2. The Identity Pool checks the token and looks up or creates the user's identity ID.
  3. The Identity Pool chooses a role using rules you configured (see below).
  4. It asks AWS STS: "let this user assume this role". The technical name of that request is AssumeRoleWithWebIdentity.
  5. STS returns temporary credentials, by default valid for one hour.
  6. The app uses those credentials to call AWS. AWS checks every call against the role's permission policies.

How the role is chosen

Method How it works Example
Default roles Every signed-in user gets one role; guests (if allowed) get another, more limited role All users get AppUserRole
Role from the token Each User Pool group can be linked to a role; the token says which group, and so which role Users in group admin get AdminRole
Rules You write "if this claim has this value, use this role" rules, checked in order Users whose department is finance get FinanceDataRole

The trust policy: who may borrow the role

Each role used by an Identity Pool must say it trusts Cognito, and should be limited to your Identity Pool and to signed-in users. Without these conditions, another Identity Pool could borrow your role.

"Condition": {
  "StringEquals": { "cognito-identity.amazonaws.com:aud": "us-east-1:<your-identity-pool-id>" },
  "ForAnyValue:StringLike": { "cognito-identity.amazonaws.com:amr": "authenticated" }
}

In plain words: "Only Cognito may hand out this role, only for this Identity Pool, and only to users who actually logged in."

One role, but each user sees only their own data

You do not need a separate role per user. A policy can include a placeholder that AWS fills in with the user's identity ID at the moment of each request:

{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-bucket/users/${cognito-identity.amazonaws.com:sub}/*"
}

This lets every user read and write only inside their own folder, users/<their-identity-id>/.

Using user details in permissions (ABAC)

Attribute-based access control means deciding access from the user's details. The Identity Pool can attach details such as department to the credentials as tags, and a policy can say "allow only if the user's department tag matches the resource's department tag".
