Setting up a credential provider, step by step

Setting up a provider means introducing AgentCore to an outside service: you register AgentCore as an app at the service, give AgentCore the resulting client ID and secret, then tell the service where AgentCore's callback lives. The example below uses Google; GitHub, Slack and the others follow the same pattern (AWS Google guide).

1. Register an OAuth app at Google

  1. In Google Cloud Console, create or pick a project and configure the OAuth consent screen: app name, support email, and bedrock-agentcore.<region>.amazonaws.com as an authorized domain.
  2. Add the scopes the agent will request, such as https://www.googleapis.com/auth/calendar.readonly.
  3. Under Credentials, create an OAuth client ID. Leave the redirect URIs empty for now.
  4. Copy the client ID and client secret.

2. Create the credential provider in AgentCore

With the AWS CLI:

aws bedrock-agentcore-control create-oauth2-credential-provider \
  --name "google-provider" \
  --credential-provider-vendor "GoogleOauth2" \
  --oauth2-provider-config-input '{
      "googleOauth2ProviderConfig": {
        "clientId": "<google-client-id>",
        "clientSecret": "<google-client-secret>"
      }
    }'

Or with the SDK:

from bedrock_agentcore.services.identity import IdentityClient

identity = IdentityClient("us-east-1")
provider = identity.create_oauth2_credential_provider({
    "name": "google-provider",
    "credentialProviderVendor": "GoogleOauth2",
    "oauth2ProviderConfigInput": {
        "googleOauth2ProviderConfig": {
            "clientId": "<google-client-id>",
            "clientSecret": "<google-client-secret>",
        }
    },
})
print(provider["callbackUrl"])

The AgentCore CLI can also add one to a project: agentcore add credential --type oauth --name ... --client-id ... --client-secret ....

3. Register AgentCore's callback URL at Google

The response includes callbackUrl, for example https://bedrock-agentcore.us-east-1.amazonaws.com/identities/oauth2/callback/<id>. Back in Google Cloud Console, add it to the OAuth client's authorized redirect URIs and save.

4. Register your app's return URL on the agent's workload identity

Add your session-binding route (for example https://app.example.com/oauth/return) to the workload identity's allowed OAuth return URLs.

5. Allow the agent to use the provider

Runtime agents created since October 2025 get the identity permissions through the service-linked role. For agents hosted elsewhere, grant the caller bedrock-agentcore:GetResourceOauth2Token (and the workload access token actions) on the relevant workload identity and provider.

6. Use it in code with @requires_access_token(provider_name="google-provider", ...).

For an API key provider, steps 1, 3 and 4 disappear:

aws bedrock-agentcore-control create-api-key-credential-provider \
  --name "weather-api-key" \
  --api-key "<the-api-key>"

For your own OAuth server, use the CustomOauth2 vendor with its discovery URL:

aws bedrock-agentcore-control create-oauth2-credential-provider \
  --name "inventory-api" \
  --credential-provider-vendor "CustomOauth2" \
  --oauth2-provider-config-input '{
      "customOauth2ProviderConfig": {
        "oauthDiscovery": {"discoveryUrl": "https://auth.example.com/.well-known/openid-configuration"},
        "clientId": "<client-id>",
        "clientSecret": "<client-secret>"
      }
    }'

These commands follow AWS's documented examples but were not run here; check the current CLI reference for exact option names.

AgentCore Gateway: inbound and outbound auth for tools

AgentCore Gateway turns APIs, Lambda functions and MCP servers into tools that agents can call through one MCP endpoint. It uses AgentCore Identity on both sides: inbound to decide which agents or users may call the gateway, and outbound to sign in to each tool behind it (AWS docs).

Inbound: who may call the gateway

  • JWT from an identity provider you trust (Cognito, Okta, Entra ID, Auth0), configured the same way as a runtime's inbound JWT authorizer. Common for agents calling on behalf of signed-in users.
  • IAM (SigV4) for AWS workloads.
  • An authenticate-only mode validates the incoming token and keeps it so it can be forwarded to the tool unchanged (token passthrough).

The gateway gets its own workload identity, just like a runtime.

Outbound: how the gateway signs in to each tool

Method What it means Works with
Gateway service role (IAM) The gateway signs requests with its own IAM role Lambda, Smithy models, API Gateway stages, MCP servers, OpenAPI, Runtime
OAuth client credentials (2LO) The gateway gets its own token from a credential provider MCP servers, OpenAPI, Smithy, Runtime
OAuth authorization code (3LO) The gateway gets the user's token, with their consent MCP servers, OpenAPI
OAuth token exchange Trades the inbound user token for one the tool accepts MCP servers, OpenAPI
API key Adds a stored key to a header or query parameter MCP servers, OpenAPI, API Gateway stages
Token passthrough Forwards the caller's token unchanged; the tool checks it Runtime targets

Outbound OAuth and API keys use the same credential providers and token vault described earlier, so a provider you set up once can serve both agents and gateways.

When to use a gateway instead of decorators in the agent

  • Many agents share the same tools. Configure credentials once on the gateway instead of in every agent.
  • You want central control: one place for policies, guardrails, logging and rate limits on tool calls.
  • Third-party agents or MCP clients call your tools and should never see your credentials.
  • Decorators in the agent remain simplest for a single agent calling a handful of APIs directly.
