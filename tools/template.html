Amazon Cognito handles logins for the apps you build, so you don't have to store passwords or invent token formats yourself. It also confuses almost everyone the first time, because it has two products with similar names, two sets of client IDs, and three kinds of tokens. This guide builds up the ideas one at a time.

Start here: the basic ideas in plain words

This document assumes no prior knowledge of login systems. Read this section first; every later section builds on these eight ideas.

1. Authentication vs authorization

  • Authentication means proving who you are. Typing a password, using Face ID, or clicking "Sign in with Google" are all authentication.
  • Authorization means deciding what you are allowed to do once we know who you are. Can you read this file? Delete that record?
  • Everyday example: at an airport, showing your passport is authentication. Your boarding pass deciding which plane and seat you get is authorization.

2. Identity provider (IdP)

An identity provider is any service that keeps user accounts and can vouch for them. Google, Microsoft (Entra ID), Okta, Facebook and Apple are identity providers. When a website lets you "Sign in with Google", Google is the IdP: it checks your password and then tells the website "yes, this is really Maya".

3. Federation

Federation means one system agrees to accept another system's word about who a user is. If your app federates with Google, your app does not store passwords at all; it trusts Google's confirmation instead.

4. Token

A token is a digital pass handed to you after you log in. Instead of sending your password with every request, your app sends the token. Like a wristband at a concert, it is quick to check, says who you are and what you may do, and expires after a while.

5. JWT (JSON Web Token)

A JWT, pronounced "jot", is the most common token format. It is a long string with three parts separated by dots:

  • a header, saying how it was signed
  • a payload, holding facts about the user (these facts are called claims)
  • a signature, a tamper-proof seal from whoever issued it

Anyone can read the payload, but nobody can change it without breaking the signature. That is how an API can trust a token without calling the issuer every time.

6. OAuth 2.0 and OpenID Connect (OIDC)

  • OAuth 2.0 is a standard set of rules for letting an app get a token to access something on a user's behalf, without the app ever seeing the user's password. It is about authorization.
  • OIDC is a thin layer on top of OAuth 2.0 that adds authentication: it defines an ID token that says who the user is.
  • Cognito, Google, Okta and almost every modern login system speak both.

7. Scopes and claims

  • A claim is a single fact inside a token, such as email: maya@example.com or groups: admin.
  • A scope is a named permission the app asked for and was granted, such as orders/read. Scopes appear inside the token as one of its claims.

8. IAM role and STS

  • In AWS, IAM (Identity and Access Management) decides who can do what to which AWS resource.
  • An IAM role is a named set of permissions, for example "may read files in this S3 bucket". Nobody owns a role permanently; you borrow it for a while.
  • STS (Security Token Service) is the AWS service that lends you a role: it hands out temporary credentials (a short-lived key) that carry that role's permissions, usually for about an hour.

The big picture

Amazon Cognito is AWS's service for handling user logins so you don't have to build them yourself. It has two main parts that do different jobs: a User Pool checks who the user is, and an Identity Pool gives that user temporary permission to use AWS services.

An office building analogy

Imagine visiting a large office building:

  1. You arrive at the front desk. They check your ID (or phone your employer to confirm you work there) and print you a visitor badge with your name and department. → This is the User Pool. The badge is a token.
  2. Your employer vouching for you over the phone is like Google or your company's login confirming who you are. → These are identity providers.
  3. The front desk only deals with approved companies, and each company has a registered account number with the building. → That account number is a client ID; it identifies which app is asking.
  4. To open doors, you take your badge to the key-card office, which gives you a key card that opens certain floors and expires tonight. → This is the Identity Pool. The key card is a set of temporary AWS credentials, and the list of doors it opens is an IAM role.

User Pools and Identity Pools

A User Pool answers "who is this person?" and an Identity Pool answers "what may this person do inside AWS?" They are separate services; you can use either one alone, or chain them together.

The User Pool: your app's login system

A User Pool is a ready-made user database plus login service, run by AWS. Without it, you would have to build sign-up pages, store passwords safely, send verification emails, and so on.

What it does for you:

  • Stores users: usernames, emails, phone numbers, and passwords (stored safely as hashes, never in plain text).
  • Runs the login: sign-up, sign-in, "forgot password", email or SMS verification, and multi-factor authentication (MFA, for example a code from an authenticator app).
  • Accepts outside logins: users can "Sign in with Google" or with their company account instead of creating a new password (covered in the next section).
  • Groups users: you can put users into groups such as admin or analyst, and the group names travel inside their tokens.
  • Hands out tokens: after a successful login, the user receives three tokens:
    • an ID token: says who the user is (name, email)
    • an access token: says what the user's app may do with your API
    • a refresh token: lets the app get fresh ID and access tokens later without asking for the password again

One important limit: these tokens are meant for your own application and API. AWS services such as S3 (file storage) or DynamoDB (a database) do not accept them directly.

The Identity Pool: a converter from login to AWS access

An Identity Pool takes a token that proves who the user is and exchanges it for temporary AWS credentials. Those credentials let the user's app call AWS services directly, for example uploading a photo straight to S3 without going through your server.

What it does, step by step:

  1. The app hands over a token from a provider the Identity Pool trusts (a User Pool, Google, a company login, and so on).
  2. The Identity Pool checks the token is genuine.
  3. It gives the user a permanent identity ID, a unique label for that person within the pool.
  4. It decides which IAM role (set of AWS permissions) this user should get.
  5. It asks AWS STS for temporary credentials for that role, typically valid for one hour, and returns them to the app.

It can also give limited access to guests who have not logged in at all, if you allow it.

How they are used together

  1. User Pool only (the most common setup). The user logs in, the app calls your API with the access token, and your server, which has its own AWS permissions, talks to AWS on the user's behalf. Users never hold AWS credentials themselves.
  2. User Pool, then Identity Pool. The user logs in, the app trades the ID token at the Identity Pool for AWS credentials, then uploads files or writes data to AWS directly. Common in mobile apps and IoT devices.
  3. Identity Pool only. Used for guest access, or when users already log in with Google or a company system and you only need to give them AWS access, without keeping your own user list.

One User Pool, two kinds of callers: people and apps

A single User Pool can serve both human users (people who log in with a password or Google) and apps that act on their own (background services, scheduled jobs, other APIs). They are stored differently: people are user records, while apps are app clients with their own client ID and secret.

Why you would want both in one place

Imagine an orders API. Customers call it from a website, and a nightly reporting job also calls it to pull totals. Both need tokens your API can check. If both kinds of token come from the same User Pool, your API checks just one issuer, one set of signing keys, and one list of scopes.

How an app logs in, step by step

  1. You define a resource server in the User Pool to represent your API, for example orders-api, and create custom scopes such as orders-api/read.
  2. You create an app client for the reporting job with a client secret, allow only the client credentials flow, and allow only the scope orders-api/read.
  3. When the job runs, it sends one request to the User Pool's /oauth2/token address containing its client ID, its secret, and the scope it wants.
  4. Cognito checks the secret and returns an access token whose scope claim says orders-api/read.
  5. The job calls the orders API with that token. The API checks the token and the scope, exactly as it would for a person.
  6. When the token expires (after one hour by default), the job simply requests a new one.

Keeping the two kinds separate inside one pool

  • Give apps and human-facing websites separate app clients. A website's app client allows the authorization code flow; a service's app client allows only client credentials. One app client cannot use both.
  • Give each service its own app client, so you can see which service did what and cancel one service's access by deleting or rotating its secret without affecting the others.
  • Grant each app client only the scopes it needs. The reporting job gets orders-api/read, never orders-api/write.
  • In your API, check token_use and client_id, and remember that an app's token has no groups: rules written as "only admins may delete" will never match an app, which is usually what you want.
  • Machine-to-machine use requires the User Pool to have a domain set up (the address that serves /oauth2/token), and AWS bills machine-to-machine token requests separately from human sign-ins, so check current Cognito pricing before relying on it heavily.

In short: people live in the pool as users and log in through a browser; apps live in the pool as app clients and log in as themselves with a secret. Both receive tokens from the same issuer, so your API treats them the same way, with scopes doing the gatekeeping.

How a User Pool works with other identity providers

A User Pool is an identity provider in its own right, and it can also pass the job of checking passwords to other providers such as Google or a company login. Either way, your app receives the same kind of Cognito tokens.

Why this matters

Users often prefer "Sign in with Google" over creating yet another password. Companies want employees to use their existing work login. Federation lets the User Pool accept both, while your app only has to understand one kind of token: Cognito's.

What happens when a user picks "Sign in with Google"

  1. The User Pool sends the user to Google's login page.
  2. Google checks the password. Cognito never sees the Google password.
  3. Google sends the user back to the User Pool with proof of who they are.
  4. The User Pool copies useful details (email, name) from Google's proof into its own user record. This copying is called attribute mapping, and you choose which details to copy.
  5. The User Pool creates a user record for this person (a federated user, with a username like Google_1098...), or links it to an existing account with the same email if you set that up.
  6. The User Pool issues its own tokens to your app. Inside the ID token, a claim called identities records that this user came through Google.

Each application registered with the User Pool can choose which providers to offer. An internal admin app might allow only the company login, while a customer app offers Google and Apple.

How identity providers trust each other

Identity providers can be chained together: one provider accepts another provider's proof, then issues its own proof to the next system. Each system only has to trust its immediate neighbour, not everyone in the chain.

An everyday comparison

Your employer confirms your identity to a travel agency. The travel agency issues you a ticket. The airline checks only the ticket; it never calls your employer. Each step trusts the one before it and issues something new.

Key ideas

  • Trust goes one way. When a User Pool trusts Google, it accepts Google's word about users. Google knows nothing about your app and does not trust the User Pool back.
  • A broker sits in the middle. Some services act as go-betweens. Cognito User Pools, Okta, Auth0 and Entra ID can all do this. Toward the provider above them, they behave like an ordinary app asking for a login. Toward the app below them, they behave like an identity provider handing out tokens.
  • Chains can have several links. A realistic example:
    1. An employee logs in with their company's Entra ID.
    2. Entra ID sends proof to the Cognito User Pool.
    3. The User Pool issues its own token to the app.
    4. The app hands that token to an Identity Pool.
    5. The Identity Pool gets AWS credentials from STS. At every hop, the receiver checks the previous proof's signature before issuing its own.
  • The format can change along the way. A company provider may speak SAML, while the User Pool hands out JWTs. The broker translates between them.
  • The Identity Pool only receives. It trusts identity providers (including User Pools), but it does not issue identity tokens; it issues AWS credentials.
  • One person, several logins. If the same person sometimes uses Google and sometimes Facebook, both logins can be linked to one user record, so their data stays the same either way.

Rule of thumb: let your app trust as few providers as possible, ideally just one broker such as a Cognito User Pool, and let the broker handle every other provider.

Client IDs and client secrets

A client ID is the name tag of an application, and a client secret is that application's password. They identify the app, not the user.

Where they come from

Before an application can use a User Pool, you register it as an app client in the User Pool. Cognito then gives it a client ID, and optionally a client secret. If you have a website, a mobile app and a background service, you would usually register three app clients, one each.

Client ID

  • A long random string, for example 4abcexampleclientid.
  • Sent with every login request so Cognito knows which app is asking.
  • Not secret. It can safely appear in website code that users can see.

Client secret

  • A second, longer string that only the app should know.
  • Proves the request really comes from that app and not an impostor using its public client ID.
  • Only safe for apps that run on a server you control (called confidential clients), because only there can the secret stay hidden.
  • Never give a secret to a website's browser code or a mobile app (called public clients). Anyone can open those and dig the secret out.

How do public clients stay safe without a secret? They use PKCE (pronounced "pixy"). At the start of the login, the app invents a random one-time code and sends a scrambled version of it. At the end, it must show the original. An attacker who intercepts the login midway cannot finish it, because they never saw the original code.

PKCE: protecting logins for apps that can't keep a secret

PKCE (Proof Key for Code Exchange, pronounced "pixy") is a one-time secret that an app invents for each login, so that only the app that started a login can finish it. It does the job a client secret would do, for apps that cannot safely hold a client secret.

The problem it solves

Recall the login flow: after the user signs in, Cognito sends the browser back to the callback URL with a short-lived authorization code, and the app swaps that code for tokens.

  • A website with a server proves it is the real app during that swap by sending its client secret. A thief holding only the code cannot complete the swap.
  • A mobile app, browser-only website or command-line tool has no safe place for a client secret; anyone can unpack the app and read it. So it has no secret.
  • Without a secret, anyone who intercepts the code (for example, a malicious app on the same phone registered to the same callback address) could swap it for tokens, because the client ID alone is public.

PKCE closes that gap with a fresh secret per login that never leaves the app until the very last step.

How it works, step by step

  1. Invent a secret. Before login, the app creates a long random string called the code verifier, for example dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk. It keeps this in memory.
  2. Scramble it. The app runs the verifier through SHA-256, a one-way scrambling function, producing the code challenge. Nobody can work backwards from the challenge to the verifier.
  3. Send only the scrambled version. The app sends the browser to Cognito's /oauth2/authorize address with its client ID, code_challenge=<challenge> and code_challenge_method=S256. Cognito remembers the challenge alongside the login.
  4. User signs in. Cognito sends the browser back to the callback URL with the authorization code, as usual.
  5. Reveal the original. The app calls /oauth2/token with the code, its client ID, and the original code verifier.
  6. Cognito checks the match. It scrambles the verifier itself; if the result equals the challenge it remembered, it issues tokens. If not, it refuses.

An attacker who steals the code in step 4 does not have the verifier, which only ever existed inside the app. They saw only the challenge (if anything), and cannot reverse it. So the stolen code is useless.

An analogy

You leave a coat at a cloakroom and tear a raffle ticket in half. The attendant keeps one half (the challenge) and you keep the other (the verifier). The paper slip they hand you (the authorization code) is not enough on its own; to collect the coat you must produce your matching half. Someone who picks up your slip cannot collect your coat.

Examples of public clients that need PKCE

A public client is any app whose code runs on a device you don't control. Anything inside it can be read by someone who digs into it, so it cannot keep a client secret and relies on PKCE instead.

Not public clients (a secret works):

  • A traditional web app with its own server (Django, Spring, Express, Rails); the secret stays on the server.
  • A backend-for-frontend server that holds tokens on behalf of a single-page app.
  • Machine-to-machine services and scheduled jobs using client credentials. They don't use PKCE at all, because there is no browser and no authorization code.

For public clients, PKCE is mandatory, because it is the only thing protecting the authorization code. For confidential clients it is still recommended as an extra layer.

Putting the three together

  • Browser-only website, mobile app, CLI: client ID + PKCE, no secret. Create the app client in Cognito without generating a secret.
  • Website with its own server: client ID + client secret. Adding PKCE as well is recommended; it blocks code interception and mix-up attacks that a secret alone does not, and newer OAuth guidance (OAuth 2.1) expects PKCE for every authorization-code login.
  • Machine-to-machine service: client ID + client secret, using the client credentials flow. PKCE does not apply, because there is no browser, no user and no authorization code.

In practice you rarely write PKCE code yourself. Libraries such as AWS Amplify, oidc-client-ts, AppAuth (for iOS and Android) and Authlib (for Python) generate the verifier and challenge for you; you just turn PKCE on.

The confusing part: two sets of client IDs

When you add "Sign in with Google" to a User Pool, you end up with two different client IDs, because there are two separate relationships: your app is a customer of Cognito, and Cognito is a customer of Google.

Why two?

Remember the broker idea from earlier. Cognito sits in the middle:

  • Looking down toward your app, Cognito is the login provider. Your app must be registered with Cognito, so your app gets a client ID from Cognito.
  • Looking up toward Google, Cognito is just another app asking Google to log someone in. So Cognito must be registered with Google, and gets a client ID from Google.

Who is asking for logins (the client) Your app Cognito
Who provides the logins (the server) Cognito Google
Where you create it Cognito console → your User Pool → App clients Google Cloud Console → Credentials → OAuth client

"Send the user back to" URL Your app's address, e.g. https://app.example.com/callback Cognito's address, ending in /oauth2/idpresponse

Your app never sees Google's client ID or secret, and never talks to Google directly. Adding Apple or a company login later repeats the pattern: one registration at that provider, for Cognito.

The whole journey, step by step

  1. The user clicks Login in your app. The app sends the browser to Cognito, including your app's client ID so Cognito knows which app this is.
  2. Cognito shows its login page with the buttons allowed for that app. The user clicks Sign in with Google.
  3. Cognito sends the browser to Google, this time including Cognito's Google client ID, so Google knows Cognito is asking.
  4. The user types their Google password on Google's own page. Google sends the browser back to Cognito with a one-time code.
  5. Behind the scenes, Cognito swaps that code with Google for proof of the user's identity, using its Google client secret.
  6. Cognito creates or finds the user in the User Pool and sends the browser back to your app with a new one-time code of its own.
  7. Your app's server swaps that code with Cognito for tokens, using your app's client ID and secret (or PKCE).
  8. The user is now logged in. If needed, the app can take the ID token to an Identity Pool to get AWS access.

Two ways to bring in Google (or any IdP)

Google can be connected to the User Pool or directly to the Identity Pool. Connecting through the User Pool is the usual choice; connecting directly is simpler but gives you less.

Option A: Google → User Pool → Identity Pool

Google is added as a login option on the User Pool, exactly as described in the previous section. The Identity Pool trusts only the User Pool.

  • The user can sign in with Google, or with any other option you allow.
  • Your app always ends up holding Cognito tokens, no matter which button was clicked.
  • If the app needs AWS access, it takes the Cognito ID token to the Identity Pool.

Option B: Google → Identity Pool directly

There is no User Pool at all. Your app shows Google's own sign-in button, gets a token from Google, and hands that Google token straight to the Identity Pool, which trusts Google directly. In code, the app passes it in a field called Logins, for example {"accounts.google.com": "<google-token>"}.

What is inside a token: claims and scopes

A Cognito token is a JWT: a sealed envelope of facts. Each fact is called a claim. One of those claims, scope, lists the scopes, meaning the permissions the token carries.

The three tokens and their jobs

Token Its job in one sentence Who reads it Default lifetime
ID token Tells the app who the user is (name, email) Your app's screens, and the Identity Pool 1 hour (adjustable from 5 minutes to 1 day)
Access token Tells your API what this request may do Your API 1 hour (adjustable from 5 minutes to 1 day)
Refresh token Gets new ID and access tokens without logging in again Your app, quietly in the background 30 days (adjustable from 1 hour to 10 years)

Short lifetimes limit the damage if a token is stolen; the refresh token avoids making users log in every hour.

What a JWT looks like

On the wire, a token is one long string like eyJraWQi... .eyJzdWIi... .Kx9f..., three parts joined by dots:

  1. Header: which algorithm signed it, and a key ID (kid) saying which of Cognito's keys was used.
  2. Payload: the claims. This part is only encoded, not encrypted, so anyone holding the token can read it. Never put secrets in it.
  3. Signature: a seal made with Cognito's private key. Your API checks it using Cognito's public keys, published at a web address ending in /.well-known/jwks.json. If even one character of the payload changes, the check fails.

Scopes: permissions with names

A scope is a label for something the app is allowed to do. The app asks for scopes when it starts the login; Cognito grants only those that are both requested and allowed on that app client.

  • Standard OIDC scopes: openid (needed to get an ID token at all), email, phone, profile (each lets the app see that part of the user's details).
  • Cognito's own scope: aws.cognito.signin.user.admin lets the user's app call Cognito to manage their own account, such as changing their phone number.
  • Custom scopes for your API: you define a resource server in the User Pool to represent your API, then invent scopes for it, written <api-name>/<permission>, for example orders-api/read and orders-api/write. Your API then checks for the scope it needs before doing the work.

Claims vs scopes in one line: claims are facts about the user and the token; scopes are the specific things the token may be used for. A Lambda function hooked into Cognito (the pre token generation trigger) can add or change claims, and with its newer version, scopes, just before the token is issued.

Resource servers and custom scopes: how they work

A resource server is a record in the User Pool that represents your API, and custom scopes are the named permissions that API understands, such as orders-api/read. Defining them lets Cognito put those permission names into access tokens, so your API can check "may this caller read orders?" without asking Cognito anything.

Where the name comes from

OAuth splits the world into roles. The authorization server issues tokens; here that is the Cognito User Pool. The resource server holds the data and accepts tokens; here that is your API, such as an orders service. Cognito does not host or run your API. A resource server in Cognito is only a description of it: a name, an identifier and a list of scopes.

What a resource server contains

Part What it is Example
Identifier A unique ID for the API. Often a URL, but any string works; it becomes the first half of every scope name orders-api or https://api.example.com/orders
Name A friendly label shown in the console Orders API
Scopes Short permission names, each with a description read ("Read orders"), write ("Create and change orders")

Cognito joins the identifier and the scope name with a slash to form the full scope string that appears in tokens and in app client settings: orders-api/read, orders-api/write. With a URL identifier you would get https://api.example.com/orders/read.

One User Pool can describe several APIs, each with its own resource server: orders-api/read, billing-api/refund, reports-api/export, and so on.

An analogy

Think of a hotel. The front desk (the User Pool) programs key cards (access tokens). Each department, such as the gym, the spa or the business lounge, is a resource server. Each department publishes which doors it has (its scopes): spa/pool, spa/sauna. The front desk writes onto your card which doors it may open; each department's door reader checks the card itself, without phoning the front desk.

How it works, from setup to API call

  1. Describe your API. Create a resource server with an identifier and its scopes. Use names that match the actions the API actually distinguishes, such as read and write, or orders.read and orders.refund for finer control.
  2. Allow scopes per app. On each app client, tick the scopes that app may ever receive (the allowed OAuth scopes), and turn on the OAuth flows it uses. This is the ceiling: an app cannot get a scope that is not allowed here.
  3. Make sure the pool has a domain. Custom scopes are issued by the OAuth endpoints (/oauth2/authorize and /oauth2/token), which live on the User Pool's domain.
  4. The app asks for scopes. It lists them in the scope parameter of its login or token request, separated by spaces: scope=openid orders-api/read.
  5. Cognito filters. It grants only scopes that are both requested and allowed for that app client. Anything else is silently dropped, or the request fails if a scope does not exist.
  6. The scopes land in the access token. The token's scope claim lists what was granted, for example "scope": "openid orders-api/read".
  7. Your API checks the scope. Before handling GET /orders it confirms the token carries orders-api/read; before POST /orders it requires orders-api/write. API Gateway can do this for you: set authorization scopes on a REST API method that uses a Cognito authorizer, or on an HTTP API route that uses a JWT authorizer.

Setting it up with the AWS CLI

# 1. Describe the API and its scopes
aws cognito-idp create-resource-server \
  --user-pool-id us-east-1_AbC123 \
  --identifier orders-api \
  --name "Orders API" \
  --scopes ScopeName=read,ScopeDescription="Read orders" \
           ScopeName=write,ScopeDescription="Create and change orders"

# 2. Create an app client for a background service that may only read
aws cognito-idp create-user-pool-client \
  --user-pool-id us-east-1_AbC123 \
  --client-name nightly-report-job \
  --generate-secret \
  --allowed-o-auth-flows client_credentials \
  --allowed-o-auth-scopes "orders-api/read" \
  --allowed-o-auth-flows-user-pool-client

The service then asks for a token

curl -X POST "https://my-app.auth.us-east-1.amazoncognito.com/oauth2/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -u "<client-id>:<client-secret>" \
  -d "grant_type=client_credentials&scope=orders-api/read"

The reply contains an access_token whose scope claim is orders-api/read. If this job asked for orders-api/write, Cognito would refuse, because that scope is not allowed on its app client.

How it differs for people and for apps

People (authorization code flow) Apps (client credentials flow)
Scopes available Standard OIDC scopes (openid, email, profile, phone), aws.cognito.signin.user.admin, and custom scopes Custom scopes only
What the app asks for Usually a mix, e.g. openid email orders-api/read Only custom scopes, e.g. orders-api/read

Things that surprise people

  • Scopes are per app, not per user. Every user who signs in through an app client can receive the same allowed scopes. Cognito does not, by itself, give orders-api/write to Alice but not to Bob. For per-user differences, use groups (the cognito:groups claim) checked in your API, or a pre token generation Lambda trigger that adds or removes scopes per user (this needs the Essentials or Plus tier).
  • API-based sign-in does not include custom scopes. If your app signs users in through the SDK's sign-in calls (for example InitiateAuth) rather than the OAuth endpoints, the access token carries only aws.cognito.signin.user.admin. To get custom scopes, sign in through managed login or the /oauth2/authorize endpoint, or add them with the pre token generation trigger.
  • Scopes are labels, not enforcement. Cognito only writes them into the token. If your API or API Gateway does not check them, they protect nothing.
  • Updating an app client replaces its settings. The update-user-pool-client command resets any setting you leave out to its default, so include the full list of scopes, flows and callback URLs every time you update.
  • Removing a scope does not cancel tokens already issued. Existing access tokens keep their old scopes until they expire.

Choosing good scopes

  • Name scopes after what the API does, such as orders-api/read and orders-api/refund, not after who uses them (avoid orders-api/admin-team).
  • Start coarse (read and write) and split later only where you truly need different access.
  • Give each app client only the scopes it uses. A reporting job never needs write.
  • Keep one resource server per API, so each API team owns its own scope list.

IAM roles and Identity Pools

An Identity Pool has no permissions of its own. Its job is to pick an IAM role for each user and get temporary credentials for it, so the role's rules decide exactly what the user can do in AWS.

A quick refresher on IAM roles

  • An IAM policy is a written rule, such as "allow reading files from the bucket my-photos".
  • An IAM role is a named bundle of policies, for example PhotoAppUserRole.
  • A role is not tied to one person. Anyone the role trusts can borrow it for a limited time. Borrowing a role is called assuming it.
  • The role's trust policy says who is allowed to borrow it. Its permission policies say what the borrower can do.

What happens when a user asks the Identity Pool for access

  1. The app sends the user's token (from the User Pool, Google, and so on).
  2. The Identity Pool checks the token and looks up or creates the user's identity ID.
  3. The Identity Pool chooses a role using rules you configured (see below).
  4. It asks AWS STS: "let this user assume this role". The technical name of that request is AssumeRoleWithWebIdentity.
  5. STS returns temporary credentials, by default valid for one hour.
  6. The app uses those credentials to call AWS. AWS checks every call against the role's permission policies.

How the role is chosen

Method How it works Example
Default roles Every signed-in user gets one role; guests (if allowed) get another, more limited role All users get AppUserRole
Role from the token Each User Pool group can be linked to a role; the token says which group, and so which role Users in group admin get AdminRole
Rules You write "if this claim has this value, use this role" rules, checked in order Users whose department is finance get FinanceDataRole

The trust policy: who may borrow the role

Each role used by an Identity Pool must say it trusts Cognito, and should be limited to your Identity Pool and to signed-in users. Without these conditions, another Identity Pool could borrow your role.

"Condition": {
  "StringEquals": { "cognito-identity.amazonaws.com:aud": "us-east-1:<your-identity-pool-id>" },
  "ForAnyValue:StringLike": { "cognito-identity.amazonaws.com:amr": "authenticated" }
}

In plain words: "Only Cognito may hand out this role, only for this Identity Pool, and only to users who actually logged in."

One role, but each user sees only their own data

You do not need a separate role per user. A policy can include a placeholder that AWS fills in with the user's identity ID at the moment of each request:

{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-bucket/users/${cognito-identity.amazonaws.com:sub}/*"
}

This lets every user read and write only inside their own folder, users/<their-identity-id>/.

Using user details in permissions (ABAC)

Attribute-based access control means deciding access from the user's details. The Identity Pool can attach details such as department to the credentials as tags, and a policy can say "allow only if the user's department tag matches the resource's department tag".

How Cognito controls what a signed-in user can access

Cognito mostly labels users rather than guarding your resources. It writes groups, scopes and other facts into the token; something else, such as API Gateway, your own code, or AWS IAM, reads those labels and allows or blocks the request.

An analogy

A conference badge says "Speaker" or "Attendee". The badge printer (Cognito) does not stand at each door. The door staff (your API, or IAM) read the badge and decide whether to let you in.

Two things to always do

  • Check every token in your API before trusting it. Verify the signature, that iss is your User Pool, that exp has not passed, that token_use is access, and that client_id is one of your apps. Standard libraries (such as aws-jwt-verify) do this for you.
  • Grant the least access needed. Give each app client only the scopes it really uses, and each IAM role only the actions it really needs.

When there is no user at all

A background service talking to your API (machine to machine) logs in as itself using the client credentials flow: it sends its client ID and secret and receives an access token. There are no users or groups here, so the token's scopes are the entire permission system.

Callback URLs and callback servers

A callback URL is the web address the login service sends the user's browser back to once login is finished. Something must be running at that address to receive the result; during testing, that "something" is a small temporary web server on your own computer, called a callback server.

Why login results arrive this way

You might expect your code to call Cognito and simply get tokens back. For logins involving a user, it does not work like that, because the user must type their password on Cognito's (or Google's) own page, not in your app. So the flow is:

  1. Your app sends the user's browser to the login page.
  2. The user logs in there.
  3. The login service sends the browser back to the callback URL, attaching a short-lived authorization code, for example: https://app.example.com/callback?code=abc123&state=xyz.
  4. Whatever is listening at that URL picks up the code and swaps it with Cognito for real tokens.

The code is a claim ticket, not the prize: it is worthless without the app's client secret or PKCE proof, and it expires within minutes.

Why an authorization code? Why not send the tokens directly?

Because the redirect back to your app travels through the browser, where it is easy to see and steal, while the code-for-tokens swap travels directly between your app and Cognito, where nobody else can see it. The code is a harmless claim ticket; the tokens are the valuables, so they never ride through the browser.

Two kinds of channel

  • The front channel is anything passed through the user's browser: redirects and the addresses they carry. It is the only way to bring the user back to your app, but it is leaky. Addresses end up in browser history, server logs and proxy logs, can be read by browser extensions, and on phones can be grabbed by a malicious app that registers the same callback address.
  • The back channel is a direct HTTPS request from your app (or its server) to Cognito's /oauth2/token address. Nothing passes through the browser, and the app chose whom it is talking to.

The authorization code flow puts only the code on the front channel and the tokens on the back channel.

Why that split matters

  1. A stolen code is useless on its own. To swap it, the thief would also need the client secret or the PKCE code verifier, which never appeared in the browser. A stolen token would work immediately.
  2. The code is short-lived and single-use. It expires within minutes and Cognito accepts it only once, so even a leaked code has a tiny window.
  3. The app proves who it is at the swap. The redirect cannot prove which app receives it, but the token request can, with the client secret or PKCE. Tokens are only ever handed to the genuine app.
  4. Refresh tokens become possible. Long-lived refresh tokens are too dangerous to put in a browser address, so a token-in-the-redirect design gives none, and users must log in again every hour. The back channel can safely deliver one.
  5. The app knows the tokens are genuine and meant for it. Tokens arrive as the answer to a request the app itself made, so an attacker cannot slip in a stolen token by crafting a fake redirect (a token injection attack).

The old way: the implicit flow

OAuth used to offer exactly what you are asking about. In the implicit flow (response_type=token), the tokens came back in the redirect itself, after a # in the address. It was designed in the days before browsers could make cross-site requests, when single-page apps had no other option.

Implicit flow (tokens in the redirect) Authorization code flow (+ PKCE)
What travels through the browser The tokens themselves Only a short-lived, single-use code
If the redirect is intercepted The attacker can use the tokens right away The attacker cannot swap the code without the secret or verifier
Proves which app receives the tokens No Yes, with the client secret or PKCE
Refresh token Not issued Issued
Exposure in history, logs, extensions High Only the harmless code
Status today Discouraged by current OAuth security guidance and dropped from OAuth 2.1 The recommended flow for every kind of app

Cognito still lets an app client enable the implicit grant for older apps. Leave it switched off, and use the authorization code flow with PKCE instead.

An analogy

A courier with a valuable parcel doesn't leave it on your doorstep, where anyone walking by could take it. They leave a collection slip (the code) in your letterbox. You then go to the depot counter (the back channel) and show the slip and your ID (the client secret or PKCE verifier) to collect the parcel (the tokens). Someone who steals the slip from your letterbox still can't collect your parcel.

Two safety features:

  • Exact registration. Cognito only sends users back to callback URLs you registered on the app client. This stops an attacker tricking Cognito into delivering codes to their own website.
  • The state value. The app sends a random value at the start and checks it comes back unchanged. This blocks a forged login response.

Why testing needs a callback server

A Jupyter notebook or a Python script has no website, so when the browser is sent back after login, there is nowhere for it to go. Starting a tiny server on localhost gives the browser somewhere to land, and lets the script catch the code. Familiar tools do the same: gcloud auth login and gh auth login briefly start a local server for exactly this reason. It is the recommended pattern for desktop and command-line apps.

What a callback server actually does: its methods

A callback server is small. For an ordinary Cognito login it answers one main route, GET /callback, plus an optional health check; everything else is helper code around it. Agent platforms add one more route of their own.

The routes it answers

Route HTTP method Called by What it does
/callback GET The user's browser, redirected by Cognito after login Reads code and state (or error), checks state, swaps the code for tokens, shows a "you can close this tab" page
/ping or /health (optional) GET Your own script or a load balancer Confirms the server is running before the login starts
Agent callback, e.g. /oauth2/callback?session_id=... (agent platforms only) GET The browser, redirected by AgentCore Identity after the user approves an outside service Checks the logged-in user, then calls CompleteResourceTokenAuth (see below)

The main route is a GET because the browser arrives by following a redirect, and redirects are always followed with GET; the code travels in the address's query string. Some identity providers can post the result to the callback instead (response_mode=form_post, a POST), but Cognito's standard flow uses GET.

What happens inside the /callback handler, step by step

  1. Read the query string. On success it holds code and state. If the user cancelled or something failed, it holds error (for example access_denied) and error_description instead; show that to the user and stop.
  2. Check state. It must equal the random value the app created just before sending the user to log in. A mismatch means the response may be forged, so reject it.
  3. Swap the code for tokens. Send a POST to Cognito's token address, https://<your-domain>.auth.<region>.amazoncognito.com/oauth2/token, with a form body containing grant_type=authorization_code, the code, the same redirect_uri used at the start (it must match exactly), the client_id, and either the PKCE code_verifier or the client secret (sent in an Authorization: Basic header).
  4. Receive the tokens. Cognito replies with JSON containing id_token, access_token, refresh_token, expires_in and token_type.
  5. Check the ID token before trusting it: signature, issuer, audience (your client ID) and expiry.
  6. Hand the tokens over. In testing, pass them to the waiting script in memory. In production, store them on the server and give the browser a session cookie.
  7. Answer the browser. In testing, a plain "Login complete, you can close this tab" page. In production, a redirect to the app's home page.
  8. Shut down (testing only). The temporary server stops once it has the tokens, or after a timeout such as two minutes.

Helper functions around it

  • Start the login: pick a port, create state and the PKCE verifier and challenge, build the /oauth2/authorize address, and open the browser.
  • Wait: block until the callback has delivered tokens or an error, with a timeout.
  • Refresh (production): later, POST to /oauth2/token with grant_type=refresh_token to get new tokens without a new login.

A minimal local callback server in Python (standard library only)

import base64, hashlib, http.server, json, secrets, threading, urllib.parse, urllib.request, webbrowser

DOMAIN = "https://my-app.auth.us-east-1.amazoncognito.com"
CLIENT_ID = "4abcexampleclientid"
REDIRECT_URI = "http://localhost:8080/callback"   # registered on the app client

state = secrets.token_urlsafe(16)                   # CSRF protection
verifier = secrets.token_urlsafe(64)                # PKCE secret, never leaves this script
challenge = base64.urlsafe_b64encode(hashlib.sha256(verifier.encode()).digest()).rstrip(b"=").decode()
result, done = {}, threading.Event()

class CallbackHandler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):                               # the browser returns here with GET
        url = urllib.parse.urlparse(self.path)
        if url.path == "/ping":                     # optional health check
            return self.reply(200, "ok")
        if url.path != "/callback":
            return self.reply(404, "Not found")
        q = urllib.parse.parse_qs(url.query)
        if "error" in q:                            # user cancelled or login failed
            result["error"] = q["error"][0]
        elif q.get("state", [""])[0] != state:      # forged or stale response
            result["error"] = "state mismatch"
        else:
            result["tokens"] = exchange_code(q["code"][0])
        self.reply(200, "Login complete. You can close this tab.")
        done.set()

    def reply(self, status, text):
        self.send_response(status)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.end_headers()
        self.wfile.write(text.encode())

def exchange_code(code):                            # POST the code to Cognito's token address
    body = urllib.parse.urlencode({
        "grant_type": "authorization_code", "code": code,
        "redirect_uri": REDIRECT_URI, "client_id": CLIENT_ID,
        "code_verifier": verifier,                  # PKCE proof instead of a client secret
    }).encode()
    req = urllib.request.Request(f"{DOMAIN}/oauth2/token", data=body,
                                 headers={"Content-Type": "application/x-www-form-urlencoded"})
    with urllib.request.urlopen(req) as resp:
        return json.load(resp)                      # id_token, access_token, refresh_token

server = http.server.HTTPServer(("localhost", 8080), CallbackHandler)
threading.Thread(target=server.serve_forever, daemon=True).start()
webbrowser.open(f"{DOMAIN}/oauth2/authorize?" + urllib.parse.urlencode({
    "response_type": "code", "client_id": CLIENT_ID, "redirect_uri": REDIRECT_URI,
    "scope": "openid email", "state": state,
    "code_challenge": challenge, "code_challenge_method": "S256"}))
done.wait(timeout=120)                              # wait up to two minutes
server.shutdown()
print(result.get("error") or f"Got tokens: {list(result['tokens'])}")

This sketch skips step 5 (checking the ID token) to stay short; use the checks from "Checking tokens in your API" before trusting the tokens.

The extra route in agent platforms (AgentCore Identity)

When an agent needs a user's approval for an outside service, AgentCore Identity sends the browser to your registered return address with a session_id in the query string (AWS docs). That handler:

  1. Reads session_id; if it is missing, answers with an error (AWS's sample returns HTTP 400).
  2. Finds out who is logged into your app in this browser, from your own session cookie.
  3. If that is the same user the agent was working for, calls CompleteResourceTokenAuth with the session (sessionUri) and the user (userIdentifier, either the user's original login token or their user ID).
  4. If the users differ, does nothing (and may log it), so a leaked approval link cannot attach a stranger's account.

The agent then asks AgentCore for the token again and receives it. Each approval link is valid for 10 minutes, and the return address must be registered as an allowed return URL on the agent's workload identity. For local testing, the AgentCore developer tooling can host this endpoint for you.

In AI agent platforms (for example AgentCore Identity)

When an agent needs access to a service such as Google Drive on a user's behalf, the user must approve it in their browser. The provider sends the browser to the agent platform's own callback, which stores the resulting token. The platform then sends the browser on to your app's callback, so your app can confirm that the person who approved is the same user the agent is working for. That check stops a leaked approval link from attaching a stranger's account. Locally this is the localhost server; in production, a route on your app.

When no callback is needed

If no person is logging in, for example a background service using the client credentials flow, or a service using a fixed API key, there is no browser and no approval screen, so there is nothing to send back and no callback URL is needed.

Part 2: Practical questions when you build

The sections above explain how the pieces fit together. The sections below answer the questions that usually come next, once you start building a real application.

Logging out and cancelling tokens

Logging out is harder than logging in, because an access token that has already been handed out keeps working until it expires. You can cancel the refresh token, but your own API may still accept a copied access token for up to its remaining lifetime.

Why access tokens can't simply be switched off

Your API checks a token by verifying its signature with Cognito's public keys. It does not phone Cognito each time; that is what makes tokens fast. The downside: if Cognito cancels a token, your API has no way of knowing, unless you add an extra check.

What actually happens on logout

Action What it does What it does not do
App deletes its stored tokens The app forgets the user, so they look logged out A copy stolen earlier still works until expiry
RevokeToken (cancel a refresh token) The refresh token can no longer get new tokens; Cognito's own APIs also reject access tokens issued from it Your API, checking signatures locally, still accepts those access tokens until they expire
GlobalSignOut Cancels all of the user's refresh tokens, on every device Same limit as above
Visit Cognito's /logout address Clears Cognito's login session cookie, so the login page asks for the password next time Does not sign the user out of Google or their company login

Practical advice

  • Keep access tokens short-lived, for example 5 to 15 minutes. A stolen token then becomes useless quickly, and refresh tokens keep users logged in meanwhile.
  • On logout, do all three: delete tokens in the app, revoke the refresh token, and send the browser to /logout if you use Cognito's login page.
  • If you truly need instant cut-off (for example, a fired employee), keep a short block list of revoked token IDs (jti) or users that your API checks, or call Cognito to check the token for sensitive actions.

Where to keep tokens in a browser or app

Whoever holds a token can act as the user, so where the app stores tokens matters as much as how it gets them. For websites, the safest common pattern is to keep tokens on your server and give the browser only a secure cookie.

The main threat: XSS

Cross-site scripting (XSS) means an attacker manages to run their own JavaScript on your web page, for example through an unsafe third-party script. Any token that page's JavaScript can read, the attacker's script can read too, and send away.

Options for websites

Where How it works Risk Good for
localStorage / sessionStorage Browser storage that JavaScript can read Stolen easily by XSS; localStorage also survives closing the browser Prototypes only
Memory (a JavaScript variable) Kept only while the page is open Still readable by XSS while the page is open; lost on refresh, so users re-login or silently refresh Single-page apps that refresh often
HTTP-only cookie set by your server The browser sends it automatically; JavaScript cannot read it XSS cannot steal it, but needs protection against forged requests (CSRF), e.g. SameSite cookies Most production websites
Backend-for-frontend (BFF) Your server holds the tokens and gives the browser only a session cookie The browser never sees a token at all The most secure option for websites

Mobile and desktop apps

Use the operating system's secure store: Keychain on iPhone and Mac, Keystore on Android, the credential manager on Windows. Never store tokens in plain files or ordinary app settings.

Services and scripts

Keep the client secret in a secrets manager such as AWS Secrets Manager, not in code or in git. Tokens can stay in memory and be fetched again when they expire.

Refresh tokens deserve the most care, because they last longest (30 days by default). Cognito can rotate refresh tokens, issuing a new one each time it is used, so a stolen old one stops working.

Checking tokens in your API: a worked example

Before your API trusts anything in a token, it must confirm six things: the signature is genuine, it came from your User Pool, it has not expired, it is the right kind of token, it was issued to one of your apps, and it carries the permission this endpoint needs. A ready-made library does all of this in a few lines.

The checks, in order

  1. Signature: fetch the User Pool's public keys from https://cognito-idp.<region>.amazonaws.com/<user-pool-id>/.well-known/jwks.json (cache them), pick the key matching the token's kid, and verify.
  2. Issuer (iss): must equal https://cognito-idp.<region>.amazonaws.com/<user-pool-id>.
  3. Expiry (exp): must be in the future.
  4. Kind (token_use): must be access for API calls.
  5. App (client_id): must be one of your app clients.
  6. Permission: the scope claim (or cognito:groups) must include what this endpoint needs.

JavaScript / TypeScript, using AWS's aws-jwt-verify library

import { CognitoJwtVerifier } from "aws-jwt-verify";

const verifier = CognitoJwtVerifier.create({
  userPoolId: "us-east-1_AbC123",
  tokenUse: "access",            // check 4
  clientId: "4abcexampleclientid", // check 5
  scope: "orders-api/read",      // check 6
});

// Checks 1-3 happen inside verify(); it throws if anything is wrong.
const claims = await verifier.verify(tokenFromAuthorizationHeader);
console.log("Request from", claims.sub);

Python, using PyJWT

import jwt
from jwt import PyJWKClient

REGION = "us-east-1"
POOL_ID = "us-east-1_AbC123"
CLIENT_ID = "4abcexampleclientid"
ISSUER = f"https://cognito-idp.{REGION}.amazonaws.com/{POOL_ID}"
jwks = PyJWKClient(f"{ISSUER}/.well-known/jwks.json")  # caches keys

def verify_access_token(token: str, required_scope: str) -> dict:
    signing_key = jwks.get_signing_key_from_jwt(token).key          # check 1
    claims = jwt.decode(
        token, signing_key, algorithms=["RS256"],
        issuer=ISSUER,                                              # check 2
        options={"verify_aud": False},  # access tokens have no 'aud'
    )                                                               # check 3 (exp) is automatic
    if claims.get("token_use") != "access":                        # check 4
        raise PermissionError("not an access token")
    if claims.get("client_id") != CLIENT_ID:                       # check 5
        raise PermissionError("unknown app")
    if required_scope not in claims.get("scope", "").split():      # check 6
        raise PermissionError("missing scope")
    return claims

Where the token comes from: the app sends it in the request header Authorization: Bearer <access token>.

Or let AWS do it: if your API sits behind API Gateway, a Cognito authorizer performs these checks before your code runs (see "Choosing an API Gateway authorizer" below).

Common mistakes

  • Decoding the payload without checking the signature. Anyone can forge an unsigned payload.
  • Accepting ID tokens at the API. They describe the user but are not meant to grant access.
  • Fetching the public keys on every request instead of caching them.

Cognito's login page vs building your own screens

You can send users to a login page that Cognito hosts for you (managed login, formerly called the hosted UI), or build your own sign-in screens that talk to Cognito through code. Most teams should start with managed login and switch only if they need full control of the look and flow.

Option 1: Managed login (Cognito's page)

  • Your app redirects the browser to Cognito's address, as described in the callback section.
  • Sign-up, sign-in, MFA, "forgot password" and the "Sign in with Google" buttons all come ready-made.
  • You can apply your logo, colours and layout with Cognito's branding editor.
  • Uses the standard OAuth flow, so it works with callback URLs, scopes and every federated provider out of the box.

Option 2: Your own screens (custom UI)

  • Your app shows its own form and calls Cognito's sign-in API directly, usually through the AWS SDK or the Amplify library.
  • The password is not sent as plain text: the default method, SRP (Secure Remote Password), proves the user knows the password without sending it.
  • Newer "choice-based" sign-in also supports passwordless options such as passkeys or one-time codes by email or SMS (on the paid feature plans).
  • "Sign in with Google" still needs a browser trip: your button sends the user to Cognito's /oauth2/authorize address with the provider named, because Google's password must be typed on Google's page.
Managed login Your own screens
Effort Low Higher: you build every screen and error message
Look and feel Branding options within Cognito's layout Anything you want
Federation (Google, SAML) Built in Still redirects through Cognito for those buttons
Security work Mostly handled by AWS You must handle errors, lockouts and messages carefully
Best for Most apps, internal tools, prototypes Consumer apps where the login must match the brand exactly

Lambda triggers: customizing each step

Lambda triggers let you run your own small piece of code at fixed moments during sign-up and sign-in. They are the main way to bend Cognito to your app's rules without building login yourself.

A Lambda function is a snippet of code that AWS runs on demand. You attach one to a named moment in the User Pool; Cognito calls it, passes in details about the user, and acts on what your code returns.

The most useful triggers

Trigger When it runs Typical use
Pre sign-up Before a new account is created Allow only certain email domains; auto-confirm trusted users; link a Google sign-in to an existing account
Post confirmation After a user verifies their email or phone Create the user's row in your own database; send a welcome email
Pre authentication Before each sign-in is checked Block users your own system has suspended
Post authentication After a successful sign-in Record login history for auditing
Pre token generation Just before tokens are issued Add claims such as tenant_id or a role from your database; on the newer version, add or remove scopes in the access token
User migration When a user who doesn't exist yet tries to sign in Check their password against your old system and move them into Cognito (see "Moving existing users")
Custom message Before Cognito sends an email or SMS Rewrite verification and reset messages in your own words and language
Custom auth challenge (define / create / verify) During a custom sign-in flow Build your own login steps, such as a magic link or a CAPTCHA

Things to know

  • Triggers run during the user's login, so they must be fast. Cognito waits only about 5 seconds for a reply, and a slow or failing trigger blocks the sign-in.
  • A trigger failure shows up to the user as a login error, so log errors clearly.
  • Customizing the access token with the pre-token-generation trigger requires one of Cognito's paid feature plans (see "Pricing tiers and limits").

Apps with many customer companies (multi-tenancy)

If you sell one app to many companies, each company is a tenant, and you must make sure one tenant's users never see another's data. With Cognito, the usual starting point is one shared User Pool with a tenant ID on every user; separate pools per tenant are for customers who need strong isolation or their own settings.

Four common designs

Design How it works Pros Cons
Shared pool + tenant attribute Every user has a custom attribute such as custom:tenant_id; it appears in the token and your API filters data by it Simplest; one place to manage; scales to many tenants Every tenant shares the same password rules, MFA settings and login page
Shared pool + group per tenant Each tenant is a User Pool group; group names appear in cognito:groups Easy to see who belongs where Groups are also used for roles, which can get confusing
Shared pool + app client per tenant Each tenant gets its own app client, with its own login options (e.g. their own company IdP) Each customer can bring their own company login More configuration per tenant
Pool per tenant Each tenant gets an entirely separate User Pool Strongest isolation; per-tenant settings, MFA and branding Much more to manage; your API must trust many issuers; AWS limits how many pools an account can have

Typical choice

  • Small and mid-size customers → shared pool with custom:tenant_id.
  • Enterprise customers who want their own company login → add an app client or SAML provider for that tenant within the shared pool.
  • Customers with strict regulatory or data-residency needs → a dedicated pool, possibly in their preferred AWS region.

Making sure the tenant ID can be trusted

  • Make custom:tenant_id read-only for apps, so users cannot change their own tenant. Set it only from your backend or a Lambda trigger.
  • Have your API take the tenant from the token, never from a request parameter the user controls.
  • If users also get AWS access through an Identity Pool, pass the tenant ID as a tag so IAM policies can enforce it too (ABAC).

User Pool vs IAM Identity Center vs IAM users

AWS has three places where "users" can live, and they serve different people. Cognito User Pools are for the users of your application. IAM Identity Center is for your employees signing into AWS and company tools. IAM users are old-style permanent AWS logins that should now be rare.

Cognito User Pool IAM Identity Center IAM user

What they log into Your website, mobile app or API The AWS console, AWS CLI, and work apps via single sign-on AWS directly

Rules of thumb

  • Building a product for outside users → Cognito.
  • Giving colleagues access to AWS accounts → IAM Identity Center.
  • A program running inside AWS (Lambda, EC2, ECS) → an IAM role attached to it, no user at all.
  • IAM users with long-term keys → avoid; use roles or Identity Center instead wherever possible.

Choosing an API Gateway authorizer

API Gateway is AWS's front door for APIs, and an authorizer is the guard at that door: it checks each request before your code runs. For Cognito tokens, pick the built-in Cognito / JWT authorizer; use a Lambda authorizer only when you need custom rules; use IAM authorization when callers hold AWS credentials from an Identity Pool.

Authorizer What the caller sends What it checks Choose it when
Cognito user pool authorizer (REST APIs) A Cognito token in the Authorization header Signature, expiry, issuer; and scopes per endpoint if you configure them You use Cognito and scopes or simple "is logged in" checks are enough
JWT authorizer (HTTP APIs) Any standard JWT, including Cognito's Signature, expiry, issuer, audience/client ID, and required scopes per route Same as above, on the cheaper, simpler HTTP API type
Lambda authorizer Any token or header Whatever your code decides, e.g. group membership, tenant, a block list You need rules beyond scopes, or a non-standard token
IAM authorization A request signed with AWS credentials (SigV4) That the credentials' IAM role is allowed to call this endpoint Callers got AWS credentials from an Identity Pool, or are other AWS services

Points to watch

  • Send access tokens, not ID tokens. The REST API's Cognito authorizer will accept an ID token if no scopes are configured on the endpoint, which is a common accident. Configure scopes so only access tokens pass.
  • The built-in authorizers check who and which scopes. Finer rules, such as "users may only see their own orders", still belong in your code.
  • Lambda authorizers can cache their decision for a few minutes to save cost, but that also delays the effect of a revoked user.

Moving existing users into Cognito

If your app already has users with passwords in another system, you usually cannot copy their passwords into Cognito, because good systems store only one-way scrambled versions (hashes) that Cognito cannot reuse. There are two ways around this.

Approach How it works User experience Best when
Bulk import (CSV) Upload a file of users and their details; no passwords Every user must reset their password on first login You can tolerate a one-time reset, or users mostly sign in with Google or a company login anyway
Just-in-time migration (user migration trigger) When an unknown user signs in, Cognito calls your Lambda function, which checks the password against the old system; if it is correct, Cognito creates the user with that same password Users notice nothing You want a smooth move and can keep the old system running for a while

A typical plan

  1. Turn on the user migration trigger and point it at the old system.
  2. Switch the app's login to Cognito. Active users migrate silently as they sign in.
  3. After a few months, bulk-import the remaining inactive users, who will reset their password if they ever return.
  4. Shut down the old login system.

Watch out for

  • The migration trigger only works with sign-in methods that send the password to Cognito, not with the SRP method; check your app's sign-in settings.
  • User IDs (sub) are new in Cognito. If your database keys data by the old ID, store the old ID as a custom attribute or keep a mapping table.

Account linking: avoiding duplicate users

By default, Cognito treats each way of signing in as a separate user. If Maya signs up with her email and password, then later clicks "Sign in with Google" using the same email, she ends up with two accounts, two sub IDs, and her data split between them. You prevent this by linking the accounts.

How linking works

  • Cognito keeps one main ("destination") user, usually the email-and-password account.
  • The Google identity is attached to it with the AdminLinkProviderForUser operation.
  • From then on, signing in either way produces tokens for the same user, with the same sub.

When to link

The usual place is the pre sign-up trigger. When a Google user signs in for the first time, the trigger looks for an existing user with the same email and, if found, links the two before Cognito creates a duplicate.

The security catch

Only link when you are sure both accounts belong to the same person:

  • Link only if the outside provider says the email is verified (Google sets email_verified).
  • Be careful with providers that let people type any email without proof. Linking on an unverified email lets an attacker take over someone's account.
  • Linking must happen before the duplicate user exists; merging two existing users later is a manual data-migration job.

Related setting: decide at the start whether users sign in with a username, an email, or a phone number. This choice (the pool's sign-in attributes) cannot be changed after the pool is created.

Regions, outages and backups

A User Pool lives in one AWS region, such as us-east-1. If Cognito in that region has an outage, nobody can sign in, and Cognito does not copy your pool to another region for you. Built-in cross-region replication has long been a top customer request (The Stack); check the current docs before designing around its absence.

What this means in practice

  • Users who are already signed in keep working until their access token expires, because your API checks tokens locally. New sign-ins and token refreshes fail.
  • You cannot export passwords, so a backup copy of the pool cannot let users sign in with their existing passwords elsewhere.
  • Choose the pool's region close to your users and in line with any data-residency rules, because moving a pool later means migrating every user.

Ways to prepare

Approach How Trade-off
Accept the risk One pool, one region; rely on AWS's in-region resilience Simplest; a regional outage blocks sign-ins
Keep settings as code Define the pool, app clients and triggers in CloudFormation, CDK or Terraform You can rebuild quickly, but users are not copied
Regular user export Periodically list users and attributes into storage you control Restores accounts, but users must reset passwords
Standby pool in a second region Copy users there; use a migration trigger or forced reset to restore passwords Most resilient; most work, and your API must accept tokens from both pools
Federate users to an outside provider Users sign in with Google or a company login Passwords live elsewhere; Cognito still brokers the login, so this only reduces, not removes, the risk

Longer access-token lifetimes soften an outage but weaken logout (see "Logging out"); choose deliberately.

Pricing tiers and limits

Each User Pool is set to one of three feature tiers: Lite, Essentials or Plus. Higher tiers unlock more features and cost more per monthly active user (MAU, a user who signs in at least once that month). You can switch a pool between tiers at any time (AWS pricing page).

Tier What it adds Notes
Lite Sign-up, password sign-in, social providers such as Google Has a free tier
Essentials Everything in Lite, plus managed login, passwordless sign-in (passkeys, email/SMS codes) and customizable access tokens Has a free tier
Plus Everything in Essentials, plus threat protection: risk-based adaptive sign-in, compromised-password detection, exporting user activity logs No free tier

What else is charged

  • Free tier: up to 10,000 MAUs per month for users who sign in directly or through social providers on Lite or Essentials, but only 50 MAUs for users who come through SAML or OIDC company providers (The Stack).
  • Machine-to-machine (apps): billed separately, per app client and per token request, with no free tier.
  • Higher request rates: available as a paid add-on if your traffic exceeds the default quotas.
  • SMS and email: Cognito sends these through Amazon SNS and SES, which bill separately.
  • Identity Pools: no extra charge; you pay only for the AWS services the credentials are used on.

Limits worth knowing

  • Cognito's APIs have requests-per-second quotas, for example on sign-ins and token requests. Busy apps or many machine clients can hit them; the quota pages list current values, and some can be raised.
  • Lambda triggers must answer within about 5 seconds.
  • An account can create only a limited number of User Pools per region, which matters for the pool-per-tenant design.

Where AgentCore Identity fits next to Cognito

Amazon Bedrock AgentCore Identity does not replace Cognito. Cognito (or another identity provider such as Okta or Entra ID) still logs in the person; AgentCore Identity manages identity around an AI agent: who may call the agent, who the agent itself is, and which outside services it may use on a person's behalf (AWS docs).

The three questions in an agent system

Question Who answers it How
Who is allowed to call this agent? (inbound) Cognito issues the token; AgentCore Identity checks it at the agent's door You point AgentCore at the User Pool, and it verifies tokens just like your API would
Who is the agent itself? AgentCore Identity Each agent gets its own workload identity, so actions can be traced to "this agent, acting for this user"
What outside services may the agent use for the user? (outbound) AgentCore Identity A token vault stores each user's tokens or API keys for services like Google Drive or Slack; if consent is missing, it runs the approval flow (see the callback section)

How it all connects

  1. The user signs in through Cognito (perhaps via Google) and the app receives a Cognito token.
  2. The app calls the agent with that token; AgentCore Identity checks it.
  3. The agent needs the user's Google Drive, so it asks AgentCore Identity for a Drive token for this user.
  4. AgentCore returns a stored token, or sends the user to approve access first.
  5. The agent calls Google Drive.

For a machine caller, such as another service invoking an agent gateway, the same User Pool can issue a client credentials token, exactly as in "One User Pool, two kinds of callers".
