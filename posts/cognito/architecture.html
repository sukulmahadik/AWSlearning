Apps with many customer companies (multi-tenancy)

If you sell one app to many companies, each company is a tenant, and you must make sure one tenant's users never see another's data. With Cognito, the usual starting point is one shared User Pool with a tenant ID on every user; separate pools per tenant are for customers who need strong isolation or their own settings.

Four common designs

Design How it works Pros Cons
Shared pool + tenant attribute Every user has a custom attribute such as custom:tenant_id; it appears in the token and your API filters data by it Simplest; one place to manage; scales to many tenants Every tenant shares the same password rules, MFA settings and login page
Shared pool + group per tenant Each tenant is a User Pool group; group names appear in cognito:groups Easy to see who belongs where Groups are also used for roles, which can get confusing
Shared pool + app client per tenant Each tenant gets its own app client, with its own login options (e.g. their own company IdP) Each customer can bring their own company login More configuration per tenant
Pool per tenant Each tenant gets an entirely separate User Pool Strongest isolation; per-tenant settings, MFA and branding Much more to manage; your API must trust many issuers; AWS limits how many pools an account can have

Typical choice

  • Small and mid-size customers → shared pool with custom:tenant_id.
  • Enterprise customers who want their own company login → add an app client or SAML provider for that tenant within the shared pool.
  • Customers with strict regulatory or data-residency needs → a dedicated pool, possibly in their preferred AWS region.

Making sure the tenant ID can be trusted

  • Make custom:tenant_id read-only for apps, so users cannot change their own tenant. Set it only from your backend or a Lambda trigger.
  • Have your API take the tenant from the token, never from a request parameter the user controls.
  • If users also get AWS access through an Identity Pool, pass the tenant ID as a tag so IAM policies can enforce it too (ABAC).

User Pool vs IAM Identity Center vs IAM users

AWS has three places where "users" can live, and they serve different people. Cognito User Pools are for the users of your application. IAM Identity Center is for your employees signing into AWS and company tools. IAM users are old-style permanent AWS logins that should now be rare.

Cognito User Pool IAM Identity Center IAM user
Who it is for Customers and users of the apps you build Your staff who work in AWS accounts and business apps A single person or program needing permanent AWS keys
What they log into Your website, mobile app or API The AWS console, AWS CLI, and work apps via single sign-on AWS directly
Typical size Thousands to millions of users Tens to thousands of employees As few as possible
Credentials Tokens for your app; AWS credentials only via an Identity Pool Short-term AWS credentials per account and role Long-term access keys and passwords
Connects to Google, Apple, SAML, OIDC Your company directory (Entra ID, Okta, Google Workspace) Nothing; stands alone
Example Maya signs into a shopping app A data engineer opens the AWS console to query Athena An old script with a hard-coded access key

Rules of thumb

  • Building a product for outside users → Cognito.
  • Giving colleagues access to AWS accounts → IAM Identity Center.
  • A program running inside AWS (Lambda, EC2, ECS) → an IAM role attached to it, no user at all.
  • IAM users with long-term keys → avoid; use roles or Identity Center instead wherever possible.

Regions, outages and backups

A User Pool lives in one AWS region, such as us-east-1. If Cognito in that region has an outage, nobody can sign in, and Cognito does not copy your pool to another region for you. Built-in cross-region replication has long been a top customer request (The Stack); check the current docs before designing around its absence.

What this means in practice

  • Users who are already signed in keep working until their access token expires, because your API checks tokens locally. New sign-ins and token refreshes fail.
  • You cannot export passwords, so a backup copy of the pool cannot let users sign in with their existing passwords elsewhere.
  • Choose the pool's region close to your users and in line with any data-residency rules, because moving a pool later means migrating every user.

Ways to prepare

Approach How Trade-off
Accept the risk One pool, one region; rely on AWS's in-region resilience Simplest; a regional outage blocks sign-ins
Keep settings as code Define the pool, app clients and triggers in CloudFormation, CDK or Terraform You can rebuild quickly, but users are not copied
Regular user export Periodically list users and attributes into storage you control Restores accounts, but users must reset passwords
Standby pool in a second region Copy users there; use a migration trigger or forced reset to restore passwords Most resilient; most work, and your API must accept tokens from both pools
Federate users to an outside provider Users sign in with Google or a company login Passwords live elsewhere; Cognito still brokers the login, so this only reduces, not removes, the risk

Longer access-token lifetimes soften an outage but weaken logout (see "Logging out"); choose deliberately.

Pricing tiers and limits

Each User Pool is set to one of three feature tiers: Lite, Essentials or Plus. Higher tiers unlock more features and cost more per monthly active user (MAU, a user who signs in at least once that month). You can switch a pool between tiers at any time (AWS pricing page).

Tier What it adds Notes
Lite Sign-up, password sign-in, social providers such as Google Has a free tier
Essentials Everything in Lite, plus managed login, passwordless sign-in (passkeys, email/SMS codes) and customizable access tokens Has a free tier
Plus Everything in Essentials, plus threat protection: risk-based adaptive sign-in, compromised-password detection, exporting user activity logs No free tier

What else is charged

  • Free tier: up to 10,000 MAUs per month for users who sign in directly or through social providers on Lite or Essentials, but only 50 MAUs for users who come through SAML or OIDC company providers (The Stack).
  • Machine-to-machine (apps): billed separately, per app client and per token request, with no free tier.
  • Higher request rates: available as a paid add-on if your traffic exceeds the default quotas.
  • SMS and email: Cognito sends these through Amazon SNS and SES, which bill separately.
  • Identity Pools: no extra charge; you pay only for the AWS services the credentials are used on.

Limits worth knowing

  • Cognito's APIs have requests-per-second quotas, for example on sign-ins and token requests. Busy apps or many machine clients can hit them; the quota pages list current values, and some can be raised.
  • Lambda triggers must answer within about 5 seconds.
  • An account can create only a limited number of User Pools per region, which matters for the pool-per-tenant design.

Prices differ by region and change over time; use the AWS pricing page and calculator for real numbers.
