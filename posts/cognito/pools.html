User Pools and Identity Pools

A User Pool answers "who is this person?" and an Identity Pool answers "what may this person do inside AWS?" They are separate services; you can use either one alone, or chain them together.

The User Pool: your app's login system

A User Pool is a ready-made user database plus login service, run by AWS. Without it, you would have to build sign-up pages, store passwords safely, send verification emails, and so on.

What it does for you:

  • Stores users: usernames, emails, phone numbers, and passwords (stored safely as hashes, never in plain text).
  • Runs the login: sign-up, sign-in, "forgot password", email or SMS verification, and multi-factor authentication (MFA, for example a code from an authenticator app).
  • Accepts outside logins: users can "Sign in with Google" or with their company account instead of creating a new password (covered in the next section).
  • Groups users: you can put users into groups such as admin or analyst, and the group names travel inside their tokens.
  • Hands out tokens: after a successful login, the user receives three tokens:
    • an ID token: says who the user is (name, email)
    • an access token: says what the user's app may do with your API
    • a refresh token: lets the app get fresh ID and access tokens later without asking for the password again

One important limit: these tokens are meant for your own application and API. AWS services such as S3 (file storage) or DynamoDB (a database) do not accept them directly.

The Identity Pool: a converter from login to AWS access

An Identity Pool takes a token that proves who the user is and exchanges it for temporary AWS credentials. Those credentials let the user's app call AWS services directly, for example uploading a photo straight to S3 without going through your server.

What it does, step by step:

  1. The app hands over a token from a provider the Identity Pool trusts (a User Pool, Google, a company login, and so on).
  2. The Identity Pool checks the token is genuine.
  3. It gives the user a permanent identity ID, a unique label for that person within the pool.
  4. It decides which IAM role (set of AWS permissions) this user should get.
  5. It asks AWS STS for temporary credentials for that role, typically valid for one hour, and returns them to the app.

It can also give limited access to guests who have not logged in at all, if you allow it.

How they are used together

  1. User Pool only (the most common setup). The user logs in, the app calls your API with the access token, and your server, which has its own AWS permissions, talks to AWS on the user's behalf. Users never hold AWS credentials themselves.
  2. User Pool, then Identity Pool. The user logs in, the app trades the ID token at the Identity Pool for AWS credentials, then uploads files or writes data to AWS directly. Common in mobile apps and IoT devices.
  3. Identity Pool only. Used for guest access, or when users already log in with Google or a company system and you only need to give them AWS access, without keeping your own user list.

One User Pool, two kinds of callers: people and apps

A single User Pool can serve both human users (people who log in with a password or Google) and apps that act on their own (background services, scheduled jobs, other APIs). They are stored differently: people are user records, while apps are app clients with their own client ID and secret.

Why you would want both in one place

Imagine an orders API. Customers call it from a website, and a nightly reporting job also calls it to pull totals. Both need tokens your API can check. If both kinds of token come from the same User Pool, your API checks just one issuer, one set of signing keys, and one list of scopes.

How an app logs in, step by step

  1. You define a resource server in the User Pool to represent your API, for example orders-api, and create custom scopes such as orders-api/read.
  2. You create an app client for the reporting job with a client secret, allow only the client credentials flow, and allow only the scope orders-api/read.
  3. When the job runs, it sends one request to the User Pool's /oauth2/token address containing its client ID, its secret, and the scope it wants.
  4. Cognito checks the secret and returns an access token whose scope claim says orders-api/read.
  5. The job calls the orders API with that token. The API checks the token and the scope, exactly as it would for a person.
  6. When the token expires (after one hour by default), the job simply requests a new one.

Keeping the two kinds separate inside one pool

  • Give apps and human-facing websites separate app clients. A website's app client allows the authorization code flow; a service's app client allows only client credentials. One app client cannot use both.
  • Give each service its own app client, so you can see which service did what and cancel one service's access by deleting or rotating its secret without affecting the others.
  • Grant each app client only the scopes it needs. The reporting job gets orders-api/read, never orders-api/write.
  • In your API, check token_use and client_id, and remember that an app's token has no groups: rules written as "only admins may delete" will never match an app, which is usually what you want.
  • Machine-to-machine use requires the User Pool to have a domain set up (the address that serves /oauth2/token), and AWS bills machine-to-machine token requests separately from human sign-ins, so check current Cognito pricing before relying on it heavily.

In short: people live in the pool as users and log in through a browser; apps live in the pool as app clients and log in as themselves with a secret. Both receive tokens from the same issuer, so your API treats them the same way, with scopes doing the gatekeeping.
