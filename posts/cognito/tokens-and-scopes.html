What is inside a token: claims and scopes

A Cognito token is a JWT: a sealed envelope of facts. Each fact is called a claim. One of those claims, scope, lists the scopes, meaning the permissions the token carries.

The three tokens and their jobs

Token Its job in one sentence Who reads it Default lifetime
ID token Tells the app who the user is (name, email) Your app's screens, and the Identity Pool 1 hour (adjustable from 5 minutes to 1 day)
Access token Tells your API what this request may do Your API 1 hour (adjustable from 5 minutes to 1 day)
Refresh token Gets new ID and access tokens without logging in again Your app, quietly in the background 30 days (adjustable from 1 hour to 10 years)

Short lifetimes limit the damage if a token is stolen; the refresh token avoids making users log in every hour.

What a JWT looks like

On the wire, a token is one long string like eyJraWQi... .eyJzdWIi... .Kx9f..., three parts joined by dots:

  1. Header: which algorithm signed it, and a key ID (kid) saying which of Cognito's keys was used.
  2. Payload: the claims. This part is only encoded, not encrypted, so anyone holding the token can read it. Never put secrets in it.
  3. Signature: a seal made with Cognito's private key. Your API checks it using Cognito's public keys, published at a web address ending in /.well-known/jwks.json. If even one character of the payload changes, the check fails.

A decoded access token payload

{
  "sub": "a1b2c3d4-1111-2222-3333-444455556666",
  "cognito:groups": ["analyst"],
  "iss": "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_AbC123",
  "client_id": "4abcexampleclientid",
  "token_use": "access",
  "scope": "openid email orders-api/read",
  "auth_time": 1760160000,
  "iat": 1760160000,
  "exp": 1760163600,
  "jti": "5e6f...",
  "username": "Google_1098..."
}

What each claim means

Claim Plain meaning
sub "Subject": the user's permanent unique ID. Use this to identify users in your database, not their email, which can change
iss "Issuer": which User Pool created the token. Your API should reject tokens from any other issuer
client_id Which app the token was issued to (access token)
aud "Audience": the same idea in the ID token, the app it was issued to
token_use Whether this is an access or id token, so one cannot be passed off as the other
scope The permissions granted, separated by spaces (access token only)
cognito:groups The User Pool groups the user belongs to
exp / iat / auth_time When it expires, when it was issued, and when the user actually logged in (in seconds since 1 January 1970)
jti A unique ID for this particular token, useful for cancelling it
email, name, custom:... Details about the user, found in the ID token
identities In the ID token: which outside provider, such as Google, the user came through

Scopes: permissions with names

A scope is a label for something the app is allowed to do. The app asks for scopes when it starts the login; Cognito grants only those that are both requested and allowed on that app client.

  • Standard OIDC scopes: openid (needed to get an ID token at all), email, phone, profile (each lets the app see that part of the user's details).
  • Cognito's own scope: aws.cognito.signin.user.admin lets the user's app call Cognito to manage their own account, such as changing their phone number.
  • Custom scopes for your API: you define a resource server in the User Pool to represent your API, then invent scopes for it, written <api-name>/<permission>, for example orders-api/read and orders-api/write. Your API then checks for the scope it needs before doing the work.

Claims vs scopes in one line: claims are facts about the user and the token; scopes are the specific things the token may be used for. A Lambda function hooked into Cognito (the pre token generation trigger) can add or change claims, and with its newer version, scopes, just before the token is issued.

Resource servers and custom scopes: how they work

A resource server is a record in the User Pool that represents your API, and custom scopes are the named permissions that API understands, such as orders-api/read. Defining them lets Cognito put those permission names into access tokens, so your API can check "may this caller read orders?" without asking Cognito anything.

Where the name comes from

OAuth splits the world into roles. The authorization server issues tokens; here that is the Cognito User Pool. The resource server holds the data and accepts tokens; here that is your API, such as an orders service. Cognito does not host or run your API. A resource server in Cognito is only a description of it: a name, an identifier and a list of scopes.

What a resource server contains

Part What it is Example
Identifier A unique ID for the API. Often a URL, but any string works; it becomes the first half of every scope name orders-api or https://api.example.com/orders
Name A friendly label shown in the console Orders API
Scopes Short permission names, each with a description read ("Read orders"), write ("Create and change orders")

Cognito joins the identifier and the scope name with a slash to form the full scope string that appears in tokens and in app client settings: orders-api/read, orders-api/write. With a URL identifier you would get https://api.example.com/orders/read.

One User Pool can describe several APIs, each with its own resource server: orders-api/read, billing-api/refund, reports-api/export, and so on.

An analogy

Think of a hotel. The front desk (the User Pool) programs key cards (access tokens). Each department, such as the gym, the spa or the business lounge, is a resource server. Each department publishes which doors it has (its scopes): spa/pool, spa/sauna. The front desk writes onto your card which doors it may open; each department's door reader checks the card itself, without phoning the front desk.

How it works, from setup to API call

  1. Describe your API. Create a resource server with an identifier and its scopes. Use names that match the actions the API actually distinguishes, such as read and write, or orders.read and orders.refund for finer control.
  2. Allow scopes per app. On each app client, tick the scopes that app may ever receive (the allowed OAuth scopes), and turn on the OAuth flows it uses. This is the ceiling: an app cannot get a scope that is not allowed here.
  3. Make sure the pool has a domain. Custom scopes are issued by the OAuth endpoints (/oauth2/authorize and /oauth2/token), which live on the User Pool's domain.
  4. The app asks for scopes. It lists them in the scope parameter of its login or token request, separated by spaces: scope=openid orders-api/read.
  5. Cognito filters. It grants only scopes that are both requested and allowed for that app client. Anything else is silently dropped, or the request fails if a scope does not exist.
  6. The scopes land in the access token. The token's scope claim lists what was granted, for example "scope": "openid orders-api/read".
  7. Your API checks the scope. Before handling GET /orders it confirms the token carries orders-api/read; before POST /orders it requires orders-api/write. API Gateway can do this for you: set authorization scopes on a REST API method that uses a Cognito authorizer, or on an HTTP API route that uses a JWT authorizer.

Setting it up with the AWS CLI

# 1. Describe the API and its scopes
aws cognito-idp create-resource-server \
  --user-pool-id us-east-1_AbC123 \
  --identifier orders-api \
  --name "Orders API" \
  --scopes ScopeName=read,ScopeDescription="Read orders" \
           ScopeName=write,ScopeDescription="Create and change orders"

# 2. Create an app client for a background service that may only read
aws cognito-idp create-user-pool-client \
  --user-pool-id us-east-1_AbC123 \
  --client-name nightly-report-job \
  --generate-secret \
  --allowed-o-auth-flows client_credentials \
  --allowed-o-auth-scopes "orders-api/read" \
  --allowed-o-auth-flows-user-pool-client

The service then asks for a token

curl -X POST "https://my-app.auth.us-east-1.amazoncognito.com/oauth2/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -u "<client-id>:<client-secret>" \
  -d "grant_type=client_credentials&scope=orders-api/read"

The reply contains an access_token whose scope claim is orders-api/read. If this job asked for orders-api/write, Cognito would refuse, because that scope is not allowed on its app client.

How it differs for people and for apps

People (authorization code flow) Apps (client credentials flow)
Scopes available Standard OIDC scopes (openid, email, profile, phone), aws.cognito.signin.user.admin, and custom scopes Custom scopes only
What the app asks for Usually a mix, e.g. openid email orders-api/read Only custom scopes, e.g. orders-api/read
If no scope is requested Cognito grants all scopes allowed on the app client Cognito grants all custom scopes allowed on the app client
Who decides per caller The app client's allowed list, plus groups or a Lambda trigger for per-user rules (see below) The app client's allowed list; each service gets its own app client

Things that surprise people

  • Scopes are per app, not per user. Every user who signs in through an app client can receive the same allowed scopes. Cognito does not, by itself, give orders-api/write to Alice but not to Bob. For per-user differences, use groups (the cognito:groups claim) checked in your API, or a pre token generation Lambda trigger that adds or removes scopes per user (this needs the Essentials or Plus tier).
  • API-based sign-in does not include custom scopes. If your app signs users in through the SDK's sign-in calls (for example InitiateAuth) rather than the OAuth endpoints, the access token carries only aws.cognito.signin.user.admin. To get custom scopes, sign in through managed login or the /oauth2/authorize endpoint, or add them with the pre token generation trigger.
  • Scopes are labels, not enforcement. Cognito only writes them into the token. If your API or API Gateway does not check them, they protect nothing.
  • Updating an app client replaces its settings. The update-user-pool-client command resets any setting you leave out to its default, so include the full list of scopes, flows and callback URLs every time you update.
  • Removing a scope does not cancel tokens already issued. Existing access tokens keep their old scopes until they expire.

Choosing good scopes

  • Name scopes after what the API does, such as orders-api/read and orders-api/refund, not after who uses them (avoid orders-api/admin-team).
  • Start coarse (read and write) and split later only where you truly need different access.
  • Give each app client only the scopes it uses. A reporting job never needs write.
  • Keep one resource server per API, so each API team owns its own scope list.

Defining claims and scopes in depth

Every claim in a Cognito token comes from one of four sources: Cognito's own bookkeeping, the user's attributes, the user's groups, or a Lambda trigger you write. Scopes come from resource servers you define, plus a few standard ones. You never type claims into a token directly; you define these sources, and Cognito assembles the token from them at sign-in.

Where each claim comes from

Source How you define it Claims it produces Which token
Cognito itself Nothing to define; always added sub, iss, exp, iat, auth_time, jti, origin_jti, token_use, client_id (access) or aud (ID), username (access) or cognito:username (ID) Both
Standard attributes Choose which ones the pool uses and which are required when you create the pool email, email_verified, phone_number, name, given_name, family_name, picture, locale and other standard OpenID Connect attributes ID token
Custom attributes Add them to the pool, e.g. tenant_id, plan custom:tenant_id, custom:plan ID token
Groups Create groups and add users to them; optionally link an IAM role and precedence cognito:groups, and with roles cognito:roles and cognito:preferred_role Both
Federation Attribute mapping on each identity provider Mapped attributes such as email, plus identities ID token
Pre token generation trigger A Lambda function that edits claims just before tokens are issued Anything you add, change or remove (within limits) ID token; access token on newer trigger versions

User attributes: the main source of identity claims

  • Standard attributes are the OpenID Connect set: email, phone_number, name, given_name, family_name, middle_name, nickname, preferred_username, picture, profile, website, gender, birthdate, zoneinfo, locale, address and updated_at.
  • Custom attributes are your own, always prefixed custom:. Each has a type (string or number), optional length or value limits, and a mutable flag that says whether it can change after sign-up.
  • Plan custom attributes carefully. You can add custom attributes later, but you cannot rename or remove them, and a required attribute cannot be added after the pool exists.
  • Values come from sign-up forms, your backend (AdminUpdateUserAttributes), attribute mapping from Google or SAML, or Lambda triggers.

Who can see and change which attributes

Each app client has its own read and write permissions for every attribute:

  • Read permission decides which attributes appear in that app client's ID token and /oauth2/userInfo response.
  • Write permission decides which attributes that app may change on the user's behalf.
  • Make sensitive attributes, such as custom:tenant_id or custom:plan, readable but not writable by apps, so users cannot promote themselves. Set them only from your backend or a trigger.

How the standard scopes relate to claims

Scope What it unlocks
openid Required to receive an ID token at all. The ID token then carries every attribute the app client is allowed to read
email email and email_verified from the /oauth2/userInfo endpoint
phone phone_number and phone_number_verified from /oauth2/userInfo
profile All attributes the app client can read, from /oauth2/userInfo
aws.cognito.signin.user.admin Lets the access token call Cognito's own user APIs, such as changing the user's attributes or password
<resource-server>/<scope> A custom permission for your API, carried in the access token's scope claim

In short: attributes and app client read permissions decide what is in the ID token; scopes decide what the access token may be used for.

Access tokens carry permissions, not profile data

By default the access token holds no email, name or custom attributes; just Cognito's own claims, cognito:groups and scope. That is deliberate: the access token is sent to APIs on every request, so it stays small and avoids leaking personal data. If an API needs, say, tenant_id, either look it up from sub, or add it to the access token with the pre token generation trigger.

Customizing claims with the pre token generation trigger

The trigger receives the claims Cognito is about to issue, and returns changes:

  • Add or override claims, such as tenant_id read from your database, or a role based on the user's plan.
  • Suppress claims you don't want exposed.
  • Override group membership shown in cognito:groups.
  • Add or remove scopes in the access token, for example granting orders-api/write only to users in the editors group. This is the way to make scopes differ per user.

The original trigger version edits only the ID token. The newer versions also edit the access token, and the latest covers machine-to-machine tokens too; these need the Essentials or Plus tier. Some claims, such as sub, iss and exp, can never be changed.

# Pre token generation trigger (newer event version): add a tenant claim and a scope
def lambda_handler(event, context):
    attrs = event["request"]["userAttributes"]
    groups = event["request"]["groupConfiguration"]["groupsToOverride"]
    scopes_to_add = ["orders-api/write"] if "editors" in groups else []
    event["response"]["claimsAndScopeOverrideDetails"] = {
        "idTokenGeneration": {
            "claimsToAddOrOverride": {"tenant_id": attrs.get("custom:tenant_id", "")}
        },
        "accessTokenGeneration": {
            "claimsToAddOrOverride": {"tenant_id": attrs.get("custom:tenant_id", "")},
            "scopesToAdd": scopes_to_add,
        },
    }
    return event

Resource servers in more depth

A resource server's identifier works like the API's address on every scope. Cognito access tokens have no audience claim naming the API they are for. Instead, the scope prefix tells each API which permissions belong to it: the orders API looks only for orders-api/... scopes and ignores billing-api/... ones. Choose identifiers that are unique and stable; changing one later changes every scope name.

Mapping scopes to API routes. A clear table of route-to-scope rules keeps an API predictable:

API route Required scope Who typically gets it
GET /orders, GET /orders/{id} orders-api/read Customer website, mobile app, reporting job
POST /orders, PATCH /orders/{id} orders-api/write Customer website, mobile app
POST /orders/{id}/refund orders-api/refund Internal support tool only
GET /orders/export orders-api/export Nightly data pipeline only

Defining it as infrastructure code (CloudFormation) keeps the scope list reviewed and versioned:

OrdersApiResourceServer:
  Type: AWS::Cognito::UserPoolResourceServer
  Properties:
    UserPoolId: !Ref UserPool
    Identifier: orders-api
    Name: Orders API
    Scopes:
      - ScopeName: read
        ScopeDescription: Read orders
      - ScopeName: write
        ScopeDescription: Create and change orders
      - ScopeName: refund
        ScopeDescription: Issue refunds
      - ScopeName: export
        ScopeDescription: Bulk export of orders

ReportingJobClient:
  Type: AWS::Cognito::UserPoolClient
  DependsOn: OrdersApiResourceServer
  Properties:
    UserPoolId: !Ref UserPool
    ClientName: nightly-report-job
    GenerateSecret: true
    AllowedOAuthFlowsUserPoolClient: true
    AllowedOAuthFlows: [client_credentials]
    AllowedOAuthScopes: [orders-api/read, orders-api/export]

The DependsOn matters: an app client can only list scopes that already exist.

Changing scopes safely

  • Adding a scope is safe. Existing tokens are unaffected; apps get it once it is allowed on their app client and they request it.
  • Updating a resource server replaces its whole scope list, so always send the complete list, not just the new scope.
  • Removing a scope: first remove it from every app client and stop checking it in the API, then delete it. Tokens already issued keep the old scope until they expire.
  • Quotas limit how many resource servers a pool can have and how many scopes each can hold (at the time of writing, 25 resource servers per pool and 100 custom scopes per resource server). Check the Cognito quotas page before designing hundreds of fine-grained scopes.

Claims and scopes together, in one sentence: define who the user is with attributes and groups (claims, mostly in the ID token), define what a caller may do with resource servers and scopes (in the access token), and use the pre token generation trigger when you need to bridge the two per user.
