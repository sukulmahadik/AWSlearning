Workload identities: the agent's own identity

A workload identity is AgentCore's identity record for one agent (or gateway). It lets the agent prove which agent is asking for a credential, separately from which user it is helping. AWS also calls this an agent identity: a workload identity with agent-specific attributes (AWS terminology).

Where workload identities live: the agent identity directory

All workload identities in an account and Region sit in an agent identity directory (today, the one named default). AWS compares it to a Cognito User Pool, but for agents instead of people: one place to list, govern and write policies for every agent identity.

Each workload identity has:

Field What it is Example
Name A unique name in the directory travel-agent
ARN Its full AWS resource name, used in IAM policies arn:aws:bedrock-agentcore:us-east-1:111122223333:workload-identity-directory/default/workload-identity/travel-agent
Allowed OAuth return URLs Your app's addresses that AgentCore may send the browser back to after a user grants consent https://app.example.com/oauth/return
Timestamps When it was created and last updated —

Because the ARN is a path, an IAM policy can target one agent (.../workload-identity/travel-agent) or every agent in the directory (.../workload-identity/*).

How workload identities are created

  • Automatically when you create an AgentCore Runtime or Gateway. The runtime's identity is linked to the service, which then fetches tokens on its behalf.
  • Manually with CreateWorkloadIdentity, for an agent you host elsewhere: on Amazon ECS, EKS, Lambda, your own servers, or another cloud. The identity works the same way wherever the agent runs.

Service-linked identities can't be used directly. A workload identity created for a Runtime or Gateway is managed by that service. If your own code tries to fetch a token for it directly, AgentCore returns an error saying the identity is linked to a service. Use the token the runtime hands your code instead.

Permissions. Agents created on or after 13 October 2025 get their identity permissions through a service-linked role, AWSServiceRoleForBedrockAgentCoreRuntimeIdentity, so you no longer attach those permissions to the execution role yourself. Older agents still need them on their execution role.

Workload access tokens: tying the agent to a user

A workload access token is a short-lived, AWS-signed token that means "this agent, acting for this user, right now". Your agent presents it every time it asks the token vault for a credential, and the vault uses it to decide whose tokens to release. AWS's terminology page calls the same idea an agent access token: one token that carries both identities, so downstream decisions can use both.

Why it exists

The token vault holds Maya's Google token, Raj's GitHub token and thousands more. When the agent asks "give me the Google token", the vault must know two things: is this really the agent the token was granted to, and which user is the agent working for? The workload access token answers both in one signed package, so the agent never has to (and can't) say "I'm working for Maya" without proof.

Three ways to get one

Call User identity comes from When to use it
GetWorkloadAccessTokenForJWT A verified JWT from the user's identity provider. AgentCore checks its signature and expiry, then uses its iss and sub claims Production. Users sign in with Cognito, Okta, Entra ID, Auth0
GetWorkloadAccessTokenForUserId A user ID string your code passes in. AgentCore does not verify it Development, quick starts, or when a trusted upstream system has already authenticated the user
GetWorkloadAccessToken No user at all The agent acts only as itself, for machine-to-machine calls

In AgentCore Runtime you rarely call these yourself. With JWT inbound auth, the runtime does it for every request:

  1. Validates the caller's JWT.
  2. Takes the user's iss and sub.
  3. Looks up the agent's workload identity.
  4. Calls GetWorkloadAccessTokenForJWT with both.
  5. Passes the result to your code in the WorkloadAccessToken request header, where the AgentCore SDK decorators pick it up automatically.

With IAM inbound auth plus the X-Amzn-Bedrock-AgentCore-Runtime-User-Id header, the runtime does the same using the user ID path instead.

Agents hosted elsewhere call these APIs directly, for example with the SDK's identity client:

from bedrock_agentcore.services.identity import IdentityClient

identity = IdentityClient("us-east-1")

# Production: prove who the user is with their verified login token
workload_token = identity.get_workload_access_token(
    workload_name="travel-agent",
    user_token=users_jwt,
)

# Development only: an unverified user ID
workload_token = identity.get_workload_access_token(
    workload_name="travel-agent",
    user_id="cognito+maya-1234",
)

Getting user IDs right

  • Take user IDs from a trusted, authenticated source, never from text the user typed.
  • If you have several identity providers, prefix IDs to avoid collisions, such as cognito+user123 and okta+user123.
  • If every caller always has a JWT, deny bedrock-agentcore:GetWorkloadAccessTokenForUserId in IAM so the unverified path can't be used at all.
  • Watch these calls in AWS CloudTrail for unexpected user IDs.
