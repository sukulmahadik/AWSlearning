Moving existing users into Cognito

If your app already has users with passwords in another system, you usually cannot copy their passwords into Cognito, because good systems store only one-way scrambled versions (hashes) that Cognito cannot reuse. There are two ways around this.

Approach How it works User experience Best when
Bulk import (CSV) Upload a file of users and their details; no passwords Every user must reset their password on first login You can tolerate a one-time reset, or users mostly sign in with Google or a company login anyway
Just-in-time migration (user migration trigger) When an unknown user signs in, Cognito calls your Lambda function, which checks the password against the old system; if it is correct, Cognito creates the user with that same password Users notice nothing You want a smooth move and can keep the old system running for a while

A typical plan

  1. Turn on the user migration trigger and point it at the old system.
  2. Switch the app's login to Cognito. Active users migrate silently as they sign in.
  3. After a few months, bulk-import the remaining inactive users, who will reset their password if they ever return.
  4. Shut down the old login system.

Watch out for

  • The migration trigger only works with sign-in methods that send the password to Cognito, not with the SRP method; check your app's sign-in settings.
  • User IDs (sub) are new in Cognito. If your database keys data by the old ID, store the old ID as a custom attribute or keep a mapping table.

Account linking: avoiding duplicate users

By default, Cognito treats each way of signing in as a separate user. If Maya signs up with her email and password, then later clicks "Sign in with Google" using the same email, she ends up with two accounts, two sub IDs, and her data split between them. You prevent this by linking the accounts.

How linking works

  • Cognito keeps one main ("destination") user, usually the email-and-password account.
  • The Google identity is attached to it with the AdminLinkProviderForUser operation.
  • From then on, signing in either way produces tokens for the same user, with the same sub.

When to link

The usual place is the pre sign-up trigger. When a Google user signs in for the first time, the trigger looks for an existing user with the same email and, if found, links the two before Cognito creates a duplicate.

The security catch

Only link when you are sure both accounts belong to the same person:

  • Link only if the outside provider says the email is verified (Google sets email_verified).
  • Be careful with providers that let people type any email without proof. Linking on an unverified email lets an attacker take over someone's account.
  • Linking must happen before the duplicate user exists; merging two existing users later is a manual data-migration job.

Related setting: decide at the start whether users sign in with a username, an email, or a phone number. This choice (the pool's sign-in attributes) cannot be changed after the pool is created.
