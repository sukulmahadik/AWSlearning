Client IDs and client secrets

A client ID is the name tag of an application, and a client secret is that application's password. They identify the app, not the user.

Where they come from

Before an application can use a User Pool, you register it as an app client in the User Pool. Cognito then gives it a client ID, and optionally a client secret. If you have a website, a mobile app and a background service, you would usually register three app clients, one each.

Client ID

  • A long random string, for example 4abcexampleclientid.
  • Sent with every login request so Cognito knows which app is asking.
  • Not secret. It can safely appear in website code that users can see.

Client secret

  • A second, longer string that only the app should know.
  • Proves the request really comes from that app and not an impostor using its public client ID.
  • Only safe for apps that run on a server you control (called confidential clients), because only there can the secret stay hidden.
  • Never give a secret to a website's browser code or a mobile app (called public clients). Anyone can open those and dig the secret out.

How do public clients stay safe without a secret? They use PKCE (pronounced "pixy"). At the start of the login, the app invents a random one-time code and sends a scrambled version of it. At the end, it must show the original. An attacker who intercepts the login midway cannot finish it, because they never saw the original code.

What an app client controls

The app client is more than an ID; it is the rulebook for that application.

Setting What it means Example
Allowed login methods (OAuth flows) Which of the standard login procedures this app may use "Authorization code" for a website; "client credentials" for a background service
Allowed scopes The maximum permissions this app can ask for openid, email, orders-api/read
Callback URLs Where Cognito may send the user back after login https://app.example.com/callback
Enabled identity providers Which login buttons appear for this app Cognito accounts and Google
Token lifetimes How long each token stays valid Access token: 60 minutes

The four types of app clients

When you create an app client in the Cognito console, it first asks what kind of application you are building: a traditional web application, a single-page application (SPA), a mobile app, or a machine-to-machine application. The choice decides the client's starting settings, above all whether it gets a client secret and which login flow it uses.

The deciding question for every type is: can this application keep a secret? Code that runs on your own server can. Code that is downloaded to a browser or installed on a phone cannot, because anyone can open it up and read it.

Traditional web application

A website whose pages are produced by your server: the browser shows HTML, but the logic, and the secret, live on the server.

  • How login works: the server redirects the browser to Cognito; Cognito sends the browser back to a route on your server with a code; the server swaps the code for tokens using its client secret (and PKCE as an extra guard).
  • Where tokens go: they stay on the server. The browser receives only a session cookie, which is the safest arrangement for a website.
  • What to configure: generate a client secret; allow the authorization code grant; register callback and sign-out URLs on your domain (https://app.example.com/callback).
  • Examples: an internal admin portal built with Django, a customer account site in Spring Boot or ASP.NET, an Express app with server-rendered pages.

Single-page application (SPA)

A web app that is downloaded once as JavaScript and then runs entirely in the browser, calling APIs directly. There is no server of your own to hold a secret.

  • How login works: the app redirects to Cognito with a PKCE challenge; Cognito returns a code to a page in the app; the browser swaps the code for tokens using the PKCE verifier.
  • Where tokens go: in the browser, ideally in memory rather than localStorage. For higher security, add a small backend-for-frontend that holds the tokens instead.
  • What to configure: no client secret; authorization code grant with PKCE; callback URLs pointing at the app (https://app.example.com/ or http://localhost:3000/ while developing). Never enable the old implicit grant.
  • Examples: a React analytics dashboard hosted on S3 and CloudFront, an Angular back-office tool, a Vue app built with AWS Amplify.

Mobile app

An app installed on a phone or tablet. The app package can be downloaded and unpacked by anyone, so it cannot contain a secret.

  • How login works: the app opens the Cognito login page in the system browser (not an embedded web view), with a PKCE challenge. Cognito returns the code to the app through a registered app link; the app swaps it using the PKCE verifier.
  • Where tokens go: the operating system's secure store: Keychain on iOS, Keystore on Android.
  • What to configure: no client secret; authorization code grant with PKCE; a callback URL that opens your app, such as a custom scheme (myapp://callback) or a universal or app link on your domain.
  • Why the system browser matters: it shares the user's existing Google or company login, and your app cannot read what the user types there. Google also blocks sign-in from embedded web views.
  • Examples: a banking or fitness app with "Sign in with Google", apps built with Swift, Kotlin, Flutter or React Native.

Machine-to-machine application

A program that calls an API as itself, with no person signing in.

  • How login works: one direct request to /oauth2/token with grant_type=client_credentials, the client ID and secret, and the scopes it wants. No browser, no callback, no code.
  • What it gets: an access token only, whose scope claim lists the custom scopes granted. There is no ID token (there is no user to describe) and no refresh token (the program simply asks again).
  • What to configure: generate a client secret; allow only the client credentials grant; allow only the custom scopes the program needs. This requires at least one resource server with custom scopes, and a User Pool domain.
  • Where the secret goes: AWS Secrets Manager or a similar store, never in code or git.
  • Examples: a nightly reporting job pulling order totals, an Airflow pipeline calling an internal data API, a microservice calling another microservice.

Things to know about app client types

  • The type is a starting template. Cognito applies sensible defaults for the type you pick, and you can adjust flows, scopes and URLs later.
  • Secret or no secret is decided at creation. Whether an app client is confidential or public is set when you create it. To switch, create a new app client.
  • One app client per application. A website and its mobile app should be separate app clients, even if they call the same API, so each gets settings that suit it and can be switched off on its own.
  • One User Pool can hold all four. The same pool can serve your website, your SPA, your mobile app and your background jobs, each through its own app client.

PKCE: protecting logins for apps that can't keep a secret

PKCE (Proof Key for Code Exchange, pronounced "pixy") is a one-time secret that an app invents for each login, so that only the app that started a login can finish it. It does the job a client secret would do, for apps that cannot safely hold a client secret.

The problem it solves

Recall the login flow: after the user signs in, Cognito sends the browser back to the callback URL with a short-lived authorization code, and the app swaps that code for tokens.

  • A website with a server proves it is the real app during that swap by sending its client secret. A thief holding only the code cannot complete the swap.
  • A mobile app, browser-only website or command-line tool has no safe place for a client secret; anyone can unpack the app and read it. So it has no secret.
  • Without a secret, anyone who intercepts the code (for example, a malicious app on the same phone registered to the same callback address) could swap it for tokens, because the client ID alone is public.

PKCE closes that gap with a fresh secret per login that never leaves the app until the very last step.

How it works, step by step

  1. Invent a secret. Before login, the app creates a long random string called the code verifier, for example dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk. It keeps this in memory.
  2. Scramble it. The app runs the verifier through SHA-256, a one-way scrambling function, producing the code challenge. Nobody can work backwards from the challenge to the verifier.
  3. Send only the scrambled version. The app sends the browser to Cognito's /oauth2/authorize address with its client ID, code_challenge=<challenge> and code_challenge_method=S256. Cognito remembers the challenge alongside the login.
  4. User signs in. Cognito sends the browser back to the callback URL with the authorization code, as usual.
  5. Reveal the original. The app calls /oauth2/token with the code, its client ID, and the original code verifier.
  6. Cognito checks the match. It scrambles the verifier itself; if the result equals the challenge it remembered, it issues tokens. If not, it refuses.

An attacker who steals the code in step 4 does not have the verifier, which only ever existed inside the app. They saw only the challenge (if anything), and cannot reverse it. So the stolen code is useless.

An analogy

You leave a coat at a cloakroom and tear a raffle ticket in half. The attendant keeps one half (the challenge) and you keep the other (the verifier). The paper slip they hand you (the authorization code) is not enough on its own; to collect the coat you must produce your matching half. Someone who picks up your slip cannot collect your coat.

Examples of public clients that need PKCE

A public client is any app whose code runs on a device you don't control. Anything inside it can be read by someone who digs into it, so it cannot keep a client secret and relies on PKCE instead.

Kind of app Familiar examples Why it can't keep a secret
Mobile apps (iOS, Android) A banking, food-delivery or fitness app with "Sign in with Google" or its own login Anyone can download and unpack the app. On phones, another app can also register the same callback address (such as myapp://callback) and catch the code, which PKCE makes useless
Single-page web apps A React, Angular or Vue dashboard served as static files, for example from S3 and CloudFront, with no server of its own All its JavaScript is downloaded to the browser and readable in developer tools
Desktop apps Electron apps (like Slack or VS Code), or a native Windows or Mac app such as a database client, that sign you in through the browser The installed program can be inspected on the user's machine
Command-line tools and scripts gcloud auth login, gh auth login, az login, aws sso login; a Python script or Jupyter notebook signing a user in through Cognito They run on the user's computer and catch the code on a localhost callback server
Other installed software Smart TV and streaming apps, browser extensions, IoT companion apps Anything a user installs or downloads can be taken apart

Not public clients (a secret works):

  • A traditional web app with its own server (Django, Spring, Express, Rails); the secret stays on the server.
  • A backend-for-frontend server that holds tokens on behalf of a single-page app.
  • Machine-to-machine services and scheduled jobs using client credentials. They don't use PKCE at all, because there is no browser and no authorization code.

For public clients, PKCE is mandatory, because it is the only thing protecting the authorization code. For confidential clients it is still recommended as an extra layer.

Putting the three together

  • Browser-only website, mobile app, CLI: client ID + PKCE, no secret. Create the app client in Cognito without generating a secret.
  • Website with its own server: client ID + client secret. Adding PKCE as well is recommended; it blocks code interception and mix-up attacks that a secret alone does not, and newer OAuth guidance (OAuth 2.1) expects PKCE for every authorization-code login.
  • Machine-to-machine service: client ID + client secret, using the client credentials flow. PKCE does not apply, because there is no browser, no user and no authorization code.

In practice you rarely write PKCE code yourself. Libraries such as AWS Amplify, oidc-client-ts, AppAuth (for iOS and Android) and Authlib (for Python) generate the verifier and challenge for you; you just turn PKCE on.
