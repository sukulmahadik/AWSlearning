The token vault and credential providers

The token vault is where AgentCore Identity keeps every credential an agent may use: OAuth access and refresh tokens, OAuth client secrets, and API keys. Credential providers are the configurations that tell AgentCore how to obtain those credentials from each outside service. Your code never sees a client secret; it asks for a token by provider name and gets one back.

The token vault

  • What it stores: OAuth 2.0 access and refresh tokens obtained for users, OAuth client credentials, and API keys (AWS features).
  • How it is protected: encrypted at rest and in transit with AWS KMS keys, either AWS-managed or your own customer-managed key.
  • Who can read what: a stored token is released only to the same agent and user combination that obtained it, and only when the agent presents a valid workload access token. Every request is checked on its own, even from callers inside the same account.
  • Refresh: when a stored access token expires and the provider gave a refresh token, AgentCore gets a new access token automatically, without asking the user again.

Think of each vault entry as labelled with three things: which agent, which user, which provider and scopes.

Agent User Provider Scopes Holds
travel-agent Maya (via Cognito) google-provider calendar.readonly Access + refresh token
travel-agent Raj (via Cognito) google-provider calendar.readonly Access + refresh token
code-review-agent Maya (via Cognito) github-provider repo Access token
travel-agent (none: the agent itself) weather-api-key — API key

The code-review-agent cannot get Maya's Google token, and the travel-agent cannot get Raj's token while working for Maya.

Credential providers

A credential provider is a named connection from AgentCore to one outside service. There are two main kinds (AWS docs):

Kind For What you give AgentCore What the agent receives
OAuth 2.0 credential provider Services that use OAuth: Google, GitHub, Slack, Salesforce, Microsoft, Atlassian, your own OAuth server The client ID and client secret you registered with that service An access token for the requested scopes
API key credential provider Services that use a single API key The API key (or the ARN of a Secrets Manager secret holding it) The API key

Built-in vs custom OAuth providers

  • Built-in vendors come with the provider's addresses already filled in. You pick a vendor and supply the client ID and secret. The list includes GoogleOauth2, GithubOauth2, SlackOauth2, SalesforceOauth2, MicrosoftOauth2, AtlassianOauth2, LinkedinOauth2, XOauth2, FacebookOauth2, OktaOauth2, Auth0Oauth2, CognitoOauth2, NotionOauth2, DropboxOauth2, ZoomOauth2, HubspotOauth2 and more (API reference).
  • CustomOauth2 works with any OAuth 2.0 provider. You give its discovery URL (or its authorization and token addresses), the client ID and the secret.

Where the secrets go. When you create an OAuth provider, AgentCore stores the client secret in AWS Secrets Manager and returns its ARN. You can let AgentCore manage that secret, or point it at a secret you already manage (clientSecretSource: EXTERNAL). API key providers work the same way.

The callback URL. Creating an OAuth provider returns a callbackUrl unique to that provider, such as https://bedrock-agentcore.us-east-1.amazonaws.com/identities/oauth2/callback/<id>. You must add it to the redirect URIs of the app you registered at Google, GitHub or Slack, because that is where the provider sends users back after they approve.

API keys

Some services skip OAuth and hand out a single API key: weather, search, maps, many AI model APIs. AgentCore Identity stores these in the token vault too, behind an API key credential provider, so the key never appears in your code, prompts or environment variables.

How it works

  1. Store the key once in an API key credential provider, either by giving AgentCore the key, or by pointing it at an existing AWS Secrets Manager secret (secretId and the JSON key that holds the value).
  2. Ask for it by name in your code with @requires_api_key(provider_name="..."). The SDK calls GetResourceApiKey with the agent's workload access token.
  3. AgentCore returns the key to that agent only, and your function receives it as an api_key argument.
from bedrock_agentcore.identity.auth import requires_api_key

@requires_api_key(provider_name="weather-api-key")
async def get_forecast(city: str, *, api_key: str) -> dict:
    # api_key is injected by AgentCore; it is never written in code or config
    ...

API keys vs OAuth

API key OAuth
Whose access Usually the agent's (one key for everyone) Per user (3LO) or the agent's (2LO)
Expiry Often none, until you rotate it Short-lived access tokens, refreshed automatically
User consent None Consent screen for user federation
Scope control Usually all-or-nothing Scopes per request
If it leaks Works for anyone until rotated Expires soon; refresh tokens can be revoked

Prefer OAuth when a service offers it, and rotate API keys regularly. Because the key lives in one place, rotating it means updating the credential provider (or its Secrets Manager secret) without redeploying the agent.
