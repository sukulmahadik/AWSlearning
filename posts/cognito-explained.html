Amazon Cognito handles logins for the apps you build, so you don't have to store passwords or invent token formats yourself. It also confuses almost everyone the first time, because it has two products with similar names, two sets of client IDs, and three kinds of tokens. This guide builds up the ideas one at a time.

Start here: the basic ideas in plain words

Everything later builds on these eight ideas.

1. Authentication vs authorization

  • Authentication means proving who you are. Typing a password, using Face ID, or clicking "Sign in with Google" are all authentication.
  • Authorization means deciding what you are allowed to do once we know who you are. Can you read this file? Delete that record?
Everyday version

At an airport, showing your passport is authentication. Your boarding pass deciding which plane and seat you get is authorization.

2. Identity provider (IdP)

An identity provider is any service that keeps user accounts and can vouch for them. Google, Microsoft Entra ID, Okta, Facebook and Apple are identity providers. When a website lets you "Sign in with Google", Google checks your password and then tells the website "yes, this is really Maya".

3. Federation

Federation means one system agrees to accept another system's word about who a user is. If your app federates with Google, your app stores no passwords; it trusts Google's confirmation instead.

4. Token

A token is a digital pass handed to you after you log in. Instead of sending your password with every request, your app sends the token. Like a wristband at a concert, it is quick to check, says who you are and what you may do, and expires after a while.

5. JWT (JSON Web Token)

A JWT, pronounced "jot", is the most common token format. It is a long string with three parts separated by dots, like the one at the top of this page:

  • a header, saying how it was signed
  • a payload, holding facts about the user, called claims
  • a signature, a tamper-proof seal from whoever issued it

Anyone can read the payload, but nobody can change it without breaking the signature. That is how an API can trust a token without calling the issuer every time.

6. OAuth 2.0 and OpenID Connect (OIDC)

  • OAuth 2.0 is a standard set of rules for letting an app get a token to access something on a user's behalf, without the app ever seeing the user's password. It is about authorization.
  • OIDC is a thin layer on top of OAuth 2.0 that adds authentication: it defines an ID token that says who the user is.

7. Scopes and claims

  • A claim is a single fact inside a token, such as email: maya@example.com or groups: admin.
  • A scope is a named permission the app asked for and was granted, such as orders-api/read. Scopes travel inside the token as one of its claims.

8. IAM role and STS

  • In AWS, IAM (Identity and Access Management) decides who can do what to which AWS resource.
  • An IAM role is a named set of permissions, such as "may read files in this S3 bucket". Nobody owns a role permanently; you borrow it for a while.
  • STS (Security Token Service) lends you a role: it hands out temporary credentials carrying that role's permissions, usually for about an hour.

The big picture

Cognito has two main parts that do different jobs. A User Pool checks who the user is. An Identity Pool gives that user temporary permission to use AWS services.

User Pools and Identity Pools

A User Pool answers "who is this person?" and an Identity Pool answers "what may this person do inside AWS?" They are separate services; you can use either alone, or chain them together.

The User Pool: your app's login system

A User Pool is a ready-made user database plus login service, run by AWS.

  • Stores users: usernames, emails, phone numbers, and passwords (as hashes, never plain text).
  • Runs the login: sign-up, sign-in, "forgot password", verification, and multi-factor authentication (MFA).
  • Accepts outside logins: users can "Sign in with Google" or with their company account.
  • Groups users such as admin or analyst; the group names travel inside tokens.
  • Hands out three tokens after login:
    • an ID token: who the user is (name, email)
    • an access token: what the app may do with your API
    • a refresh token: gets fresh tokens later without the password

These tokens are meant for your own app and API. AWS services such as S3 or DynamoDB do not accept them directly.

The Identity Pool: a converter from login to AWS access

An Identity Pool exchanges a token that proves who the user is for temporary AWS credentials, so the app can call AWS services directly, for example uploading a photo straight to S3.

  1. The app hands over a token from a provider the Identity Pool trusts.
  2. The Identity Pool checks the token is genuine.
  3. It gives the user a permanent identity ID within the pool.
  4. It decides which IAM role this user should get.
  5. It asks STS for temporary credentials for that role, typically valid for one hour.

It can also give limited access to guests who have not logged in, if you allow it.

How they are used together

  1. User Pool only (most common). The app calls your API with the access token; your server uses its own AWS permissions. Users never hold AWS credentials.
  2. User Pool, then Identity Pool. The app trades the ID token for AWS credentials and writes to AWS directly. Common in mobile and IoT apps.
  3. Identity Pool only. For guest access, or when users already log in with Google or a company system and you only need AWS access.

One User Pool, two kinds of callers: people and apps

A single User Pool can serve human users and apps that act on their own, such as background services or scheduled jobs. People are stored as user records; apps are app clients with their own client ID and secret.

Imagine an orders API. Customers call it from a website, and a nightly reporting job also calls it to pull totals. If both kinds of token come from one User Pool, your API checks just one issuer, one set of signing keys, and one list of scopes.

How an app logs in

  1. Define a resource server for your API, such as orders-api, with scopes like orders-api/read.
  2. Create an app client for the job with a client secret, allowing only the client credentials flow and only orders-api/read.
  3. The job sends its client ID, secret and requested scope to /oauth2/token.
  4. Cognito returns an access token whose scope claim says orders-api/read.
  5. The job calls the API with it; the API checks it exactly as it would a person's token.
  6. When it expires, the job simply asks again.

Keeping them separate

  • Use separate app clients for websites (authorization code) and services (client credentials).
  • Give each service its own app client, so you can trace and cut off one without affecting others.
  • Grant each app client only the scopes it needs.
  • An app's token has no groups, so a rule like "only admins may delete" never matches an app.
  • Machine-to-machine needs a User Pool domain, and AWS bills its token requests separately from human sign-ins.

How a User Pool works with other identity providers

A User Pool is an identity provider in its own right, and it can also hand the password check to other providers such as Google or a company login. Either way, your app receives the same Cognito tokens.

What happens when a user picks "Sign in with Google"

  1. The User Pool sends the user to Google's login page.
  2. Google checks the password. Cognito never sees it.
  3. Google sends the user back to the User Pool with proof of identity.
  4. The User Pool copies chosen details, such as email and name (attribute mapping).
  5. It creates a federated user (username like Google_1098…) or links to an existing account.
  6. It issues its own tokens. The ID token's identities claim records that the user came via Google.

Each app client chooses which providers to offer: an internal tool might allow only the company login, while a customer app offers Google and Apple.

How identity providers trust each other

Identity providers can be chained: one accepts another's proof, then issues its own proof to the next system. Each only trusts its immediate neighbour.

Everyday version

Your employer confirms your identity to a travel agency, which issues a ticket. The airline checks only the ticket; it never calls your employer.

  • Trust goes one way. A User Pool trusts Google; Google knows nothing about your app.
  • A broker sits in the middle. Cognito User Pools, Okta, Auth0 and Entra ID can act like an ordinary app toward the provider above and like an identity provider toward the app below.
  • Chains can be long. Entra ID → User Pool → app → Identity Pool → STS. Each hop checks the previous signature before issuing its own.
  • Formats change along the way. SAML in, JWT out; the broker translates.
  • The Identity Pool only receives. It trusts providers but issues AWS credentials, not identity tokens.
  • One person, several logins can be linked to one user record.

Rule of thumb: let your app trust one broker, and let the broker handle every other provider.

Client IDs and client secrets

A client ID is an application's name tag; a client secret is that application's password. They identify the app, not the user.

Before an app can use a User Pool, you register it as an app client. A website, a mobile app and a background service would usually be three app clients.

  • Client ID: a public random string, sent with every login request. Safe in browser code.
  • Client secret: proves the request really comes from that app. Only for apps on a server you control (confidential clients). Never put one in browser code or a mobile app (public clients); anyone can dig it out.

PKCE: protecting logins for apps that can't keep a secret

PKCE (Proof Key for Code Exchange, pronounced "pixy") is a one-time secret an app invents for each login, so only the app that started a login can finish it. It does the job of a client secret for apps that cannot safely hold one.

The problem it solves

After sign-in, Cognito sends the browser back with a short-lived authorization code, which the app swaps for tokens.

  • A website with a server proves itself during that swap with its client secret.
  • A mobile app, browser-only site or CLI has no safe place for a secret, so it has none.
  • Without a secret, anyone who intercepts the code could swap it, because the client ID is public.

How it works

  1. Invent a secret. The app creates a long random code verifier, e.g. dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk, kept in memory.
  2. Scramble it. SHA-256 turns it into the code challenge, which cannot be reversed.
  3. Send only the scrambled version to /oauth2/authorize with code_challenge_method=S256. Cognito remembers it.
  4. User signs in; the browser returns with the code.
  5. Reveal the original. The app calls /oauth2/token with the code and the original verifier.
  6. Cognito checks the match and only then issues tokens.

A thief holding the code never saw the verifier, so the code is useless to them.

The confusing part: two sets of client IDs

Adding "Sign in with Google" creates two different client IDs, because there are two relationships: your app is a customer of Cognito, and Cognito is a customer of Google.

The whole journey

  1. The user clicks Login; the app sends the browser to Cognito with your app's client ID.
  2. Cognito shows the buttons allowed for that app; the user picks Google.
  3. Cognito sends the browser to Google with Cognito's Google client ID.
  4. The user signs in on Google's page; Google returns a code to Cognito.
  5. Cognito swaps that code with Google using its Google client secret.
  6. Cognito creates or finds the user and returns a new code to your app.
  7. Your app swaps it for tokens using your client ID and secret, or PKCE.
  8. Optionally, the app takes the ID token to an Identity Pool for AWS access.

Two ways to bring in Google (or any IdP)

Option A: Google → User Pool → Identity Pool. Google is a login option on the User Pool; your app always holds Cognito tokens.

Option B: Google → Identity Pool directly. No User Pool. The app gets Google's token itself and passes it in Logins, e.g. {"accounts.google.com": "<google-token>"}.

Scopes: permissions with names

  • Standard OIDC: openid (needed for an ID token), email, phone, profile.
  • Cognito's own: aws.cognito.signin.user.admin lets users manage their own account.
  • Custom: define a resource server for your API and scopes like orders-api/read.

Cognito grants only scopes that are both requested and allowed on the app client. Claims describe the user and token; scopes describe what the token may be used for. The pre token generation trigger can add claims, and on its newer version, scopes.

IAM roles and Identity Pools

An Identity Pool has no permissions of its own. It picks an IAM role for each user and gets temporary credentials for it; the role's rules decide what the user can do.

  • An IAM policy is a written rule; an IAM role bundles policies.
  • Borrowing a role is assuming it. The trust policy says who may borrow; permission policies say what the borrower can do.
How the role is chosenHow it worksExample

The trust policy

"Condition": {
  "StringEquals": { "cognito-identity.amazonaws.com:aud": "us-east-1:<your-identity-pool-id>" },
  "ForAnyValue:StringLike": { "cognito-identity.amazonaws.com:amr": "authenticated" }
}

In plain words: only Cognito may hand out this role, only for this Identity Pool, and only to users who logged in.

One role, each user sees only their own data

{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-bucket/users/${cognito-identity.amazonaws.com:sub}/*"
}

AWS fills in each user's identity ID, so everyone is confined to users/<their-id>/. With ABAC, the Identity Pool can also tag credentials with details like department for policies to check.

How Cognito controls what a signed-in user can access

Cognito mostly labels users rather than guarding resources. It writes groups, scopes and facts into the token; API Gateway, your code or IAM reads them and allows or blocks.

Callback URLs and callback servers

A callback URL is where the login service sends the browser after login. Something must be listening there; during testing, that is a small temporary web server on your own computer, a callback server.

  1. Your app sends the user's browser to the login page.
  2. The user logs in there, not in your app.
  3. The browser is sent back with a short-lived code: https://app.example.com/callback?code=abc123&state=xyz.
  4. Whatever listens there swaps the code for tokens.

Cognito only redirects to registered URLs, and the app checks that state comes back unchanged, which blocks forged responses.

TestingProduction
ListeningTemporary server at http://localhost:8080/callbackA /callback route on your site or backend
Registered URLPlain http allowed only for localhosthttps:// on your domain
Runs forThe few seconds of loginAlways

A notebook or script has no website, so the browser has nowhere to land; a tiny localhost server fixes that. gcloud auth login and gh auth login do exactly this.

In agent platforms such as AgentCore Identity, the provider returns first to the platform's callback, which stores the token, then to your app's callback so your app can confirm the approving user is the user the agent works for. Background services using client credentials or API keys need no callback at all.

Part 2 · Practical questions when you build

Logging out and cancelling tokens

An access token that has been handed out keeps working until it expires, because your API checks signatures locally and never asks Cognito.

ActionDoesDoesn't
App deletes tokensThe user looks logged outStop a copy stolen earlier
RevokeTokenRefresh token can't get new tokens; Cognito's APIs reject its access tokensStop your API accepting them until expiry
GlobalSignOutCancels refresh tokens on every deviceSame limit
Cognito /logoutClears Cognito's session cookieSign the user out of Google
  • Keep access tokens short-lived (5 to 15 minutes).
  • On logout, delete tokens, revoke the refresh token, and visit /logout.
  • For instant cut-off, keep a small block list of revoked jti values or users.

Where to keep tokens in a browser or app

Whoever holds a token can act as the user. For websites, the safest common pattern keeps tokens on your server and gives the browser only a secure cookie. The main threat is XSS: an attacker's script on your page can read anything your JavaScript can.

WhereRiskGood for
localStorageEasily stolen by XSS; persistsPrototypes only
MemoryReadable by XSS while open; lost on refreshSingle-page apps that refresh silently
HTTP-only cookieNot readable by script; needs CSRF protectionMost production sites
Backend-for-frontendBrowser never sees a tokenThe most secure option

Mobile apps use Keychain (Apple) or Keystore (Android). Services keep the client secret in a secrets manager. Refresh tokens deserve the most care; rotate them where you can.

Checking tokens in your API: a worked example

  1. Signature against the pool's cached public keys.
  2. Issuer equals https://cognito-idp.<region>.amazonaws.com/<pool-id>.
  3. Expiry in the future.
  4. Kind: token_use is access.
  5. App: client_id is yours.
  6. Permission: the needed scope is present.

JavaScript, with aws-jwt-verify

import { CognitoJwtVerifier } from "aws-jwt-verify";

const verifier = CognitoJwtVerifier.create({
  userPoolId: "us-east-1_AbC123",
  tokenUse: "access",              // check 4
  clientId: "4abcexampleclientid", // check 5
  scope: "orders-api/read",        // check 6
});

// Checks 1-3 happen inside verify(); it throws if anything is wrong.
const claims = await verifier.verify(tokenFromAuthorizationHeader);

Python, with PyJWT

import jwt
from jwt import PyJWKClient

POOL_ID = "us-east-1_AbC123"
CLIENT_ID = "4abcexampleclientid"
ISSUER = f"https://cognito-idp.us-east-1.amazonaws.com/{POOL_ID}"
jwks = PyJWKClient(f"{ISSUER}/.well-known/jwks.json")  # caches keys

def verify_access_token(token: str, required_scope: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token).key           # check 1
    claims = jwt.decode(token, key, algorithms=["RS256"],
                        issuer=ISSUER,                         # check 2, 3
                        options={"verify_aud": False})         # access tokens have no aud
    if claims.get("token_use") != "access":                   # check 4
        raise PermissionError("not an access token")
    if claims.get("client_id") != CLIENT_ID:                  # check 5
        raise PermissionError("unknown app")
    if required_scope not in claims.get("scope", "").split(): # check 6
        raise PermissionError("missing scope")
    return claims

Common mistakes: decoding without checking the signature, accepting ID tokens at the API, and fetching keys on every request.

Send access tokens, not ID tokens. The REST Cognito authorizer accepts ID tokens when no scopes are configured; configure scopes so only access tokens pass.

Moving existing users into Cognito

Passwords usually can't be copied, because good systems store only hashes Cognito can't reuse.

  • Bulk CSV import: no passwords; everyone resets on first login.
  • User migration trigger: on an unknown sign-in, your Lambda checks the old system; if correct, Cognito creates the user with the same password. Users notice nothing.

Typical plan: enable the trigger, switch login to Cognito, bulk-import stragglers months later, then retire the old system. The trigger needs a sign-in method that sends the password (not SRP), and sub values are new, so keep a mapping from old IDs.

Account linking: avoiding duplicate users

By default each way of signing in is a separate user: Maya with a password and Maya via Google become two accounts. Link them with AdminLinkProviderForUser, usually from the pre sign-up trigger, before the duplicate is created.

  • Link only when the provider says the email is verified, or an attacker could take over the account.
  • Merging two existing users later is a manual data job.
  • Choose username, email or phone sign-in at the start; it can't be changed after the pool exists.

Regions, outages and backups

A User Pool lives in one AWS region. If Cognito there is down, new sign-ins fail, though users with unexpired access tokens keep working. Cognito has not offered built-in cross-region replication, a long-standing request (The Stack); check current docs.

  • Keep the pool's settings as code (CloudFormation, CDK, Terraform).
  • Export users regularly; passwords can't be exported, so restores need resets.
  • For high resilience, run a standby pool in a second region, with your API accepting both issuers.

Pricing tiers and limits

Each User Pool is on one tier, switchable at any time (AWS pricing):

TierAdds
LiteSign-up, password sign-in, social providers
EssentialsManaged login, passwordless, customizable access tokens
PlusThreat protection: adaptive sign-in, compromised-password detection, activity log export
  • Lite and Essentials include 10,000 free monthly active users for direct and social sign-ins, but only 50 for SAML/OIDC users.
  • Machine-to-machine is billed per app client and token request, with no free tier.
  • SMS and email bill through SNS and SES. Identity Pools cost nothing extra.
  • APIs have requests-per-second quotas; higher rates are a paid add-on.

Where AgentCore Identity fits next to Cognito

Amazon Bedrock AgentCore Identity doesn't replace Cognito. Cognito still logs in the person; AgentCore Identity manages identity around an AI agent (AWS docs).

QuestionAnswered by
Who may call the agent? (inbound)Cognito issues the token; AgentCore checks it
Who is the agent itself?AgentCore gives each agent a workload identity
Which outside services may it use for the user? (outbound)AgentCore's token vault stores per-user tokens and runs consent flows

A user signs in via Cognito, calls the agent, the agent asks AgentCore for the user's Google Drive token, and calls Drive. Machine callers use client credentials from the same User Pool.
